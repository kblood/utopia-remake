# Project instructions

## Objective

Decompile and recreate Amiga Utopia as a standalone engine that runs using game files supplied by the player. ScummVM is an analogy for loading user-provided files, not a required framework or integration target. Keep game code and loaders in this repository; do not bundle or commit the original game's disks, assets, or executable data. Read `README.md`, `notes/ARCHITECTURE.md`, and relevant `notes/formats/*.md` before changing engine behavior. Treat VERIFIED and HYPOTHESIS labels as evidence levels, not interchangeable facts.

The current implementation is TypeScript + Canvas 2D and recognizes the user's WHDLoad 1.2 (0757) game files. Do not imply ADF/HDF/IPF mounting or compatibility with other releases unless implemented and verified. Disk.4 data decoders and preparation layers are documented in `notes/formats/game-proper.md`. `prepareDisk4EnemyLoad()` returns detached fixed-slot enemies. `prepareDisk4HeadlessEnemies()` inertly adopts those exact objects and slots, plus the `ShipRoster` (ships and distinct `RestoredMissile`s into `sim.fleet`), into one composed `EnemySystem`, all-or-error: crushers whose `+$13` counter exceeds 7 or whose `+$14` animation exceeds the table `$12D60` maximum (other crusher states are adopted: `+$13` = toggle bit 7 + counter, `+$14` = animation, see enemies.md section 3a), missile modes other than 1/2/4, lift above $7F, non-playable `+$14` pointers and a mismatching `$1429E` count fail with typed errors before anything is installed. Adoption performs no `createShip`, initialization, RNG, hooks, or buffer/state writes; callers advance enemy movement through explicit `pass(clock)` calls, while `Sim.loopPass()` consumes traced gun periods; `frame()` remains a legacy no-op. Ship extras are seeded from saved `+6/+7`, `+$11`, `+$12` and the `+$14` reservation cell; restored missiles follow the traced `$4408`/`$ACE2` behaviour and resolve the current occupant of their saved enemy slot at run time (traces and confidence limits in `notes/formats/ship-control.md` 5c; restored ship landing is statically traced and synthetically covered, without an emulator comparison). Enemy spawn/defection allocate the first free fixed slot (verified against original scans). The headless continuation is now attachable through an experimental live `MapScene` and the browser disk menu when the picked WHDLoad folder includes `disk.4`. `Game.activateDisk4()` reads the saved scenario-disk id at `$1453E` and scenario index at `$135C2`, matching the original `$888A`-`$88AA` load path, and writes `$8F96 + index*$40` to runtime `$1453A`; map comparison is advisory and an explicit recovery choice is available only for an invalid saved index. The activation applies the traced `$875C`-`$87DA` runtime reset and clears the 30 effect slots at `$88DC`-`$88E6`, while other post-load work remains incomplete. It preserves the prepared graph and is backed by static traces and synthetic tests, but original post-load fidelity is unverified; it is not a claim of full playable restore. Imported Disk.4 sessions are refused by the native-save provenance policy; version-10 native saves include runtime entities, hardware-approximation counters, exact main-loop phase and pending modal-return pass, the `$156A9` bit-5 blast mark (version 10; versions 2-9 migrate with it clear), all 30 fixed effect slots with holes (gameplay-relevant: a full pool changes the occupancy outcome of a combat explosion; versions 2-5 never stored effects and migrate with an empty pool, while versions 6-7 stored a dense list and migrate with assumed slot numbers) and the raw `+$16` flag pointer of every enemy fixed slot, free slots included (per the static Disk.1 trace the pointer belongs to the slot: wave spawn `$48B6`/`$48EC` leaves it untouched, the first movement claim overwrites it, and `$4732` releases the cell the stored, possibly stale or zero, pointer names, not x/y; versions 2-6 never stored it and migrate with occupied pointers derived from the saved reservation cell and free ones set to 0, a lossy assumption shown in the slot label; the zero default of never-used slots rests on one external pre-November snapshot and is not proven for first-boot RAM; `EnemyRoster` preserves the raw pointers of occupied and free Disk.4 slots exactly), while original Disk.4 export/roundtrip remains unavailable, and the memory-derived capture described in the format notes is not a persisted save.

## Reverse-engineering workflow

- Prefer behavioral evidence from the running original (WinUAE/Copperline) and static evidence from the original program image. Record observations in the relevant format note, distinguish observations from hypotheses, then implement the behavior in the engine.
- Keep the engine independent of proprietary game data; read original files locally at runtime.
- Before editing, inspect the current code and notes. Avoid stale status claims; update documentation when implementation status changes.
- Do not claim fidelity from compilation alone. Run the relevant checks when requested or needed, and report what was actually verified.
