# Runtime checkpoints (remake instrumentation for original-vs-remake comparison)

Status: implemented in `src/game/checkpoint.ts` (schema 4: post-redraw cycle boundary; fixed 30-slot effects were added in schema 3, see section 3), wired into `MapScene` (`enableCheckpoints`, `disableCheckpoints`, `captureCheckpoint`), covered by `test/checkpoint.mjs`. This is instrumentation of the REMAKE, not an observation of the original: it makes the remake's state readable at well-defined points so that values seen in the running original (WinUAE / Copperline debugger, `notes/formats/map-rendering.md` section 6 "Main-loop timing") can be compared with it. Field meanings keep the evidence level of the note that documents each address; `approximations.hardware` records only the remake's deterministic stand-in stream counters for CIA/raster reads, not original hardware values. Original comparisons remain bounded: the tank route, monthly production and one RAM-staged invasion slice are separately described below and in their format notes; none establishes broad gameplay parity.

## 1. Contract

- **Opt-in.** Nothing is captured unless a caller asks. `scene.enableCheckpoints(options?)` returns a `CheckpointRecorder`; `scene.captureCheckpoint(options?)` returns one `RuntimeCheckpoint` without a recorder (boundary `"manual"`). `scene.disableCheckpoints()` stops recording; the recorder keeps what it stored.
- **Read-only.** Capture only reads. It writes no state byte, map word, flag byte, object record or counter, draws no RNG value, calls no game hook, and does not look at input. Two passive read paths exist in the game classes: `EnemySystem.inspectShip()` (copy of a ship's extra state; never creates the lazily created extra of a ship) and `Messages.observer` / `Messages.inspect()` (the observer is told each message request before it is handled; `inspect()` returns timers and shape without text). A throwing capture or `onCheckpoint` callback is caught and counted (`recorder.failures`, `lastError`), never propagated into the loop. `test/checkpoint.mjs` runs the same synthetic loop, and the same 400-update `MapScene` run (needs the local Disk.1/Disk.2), with and without capture and compares state image, map words, flag bytes, object records, slots, view, pass clock, RNG draws and (scene) the screen.
- **No persistence, no logging, no network.** Checkpoints live in the memory of the recorder (bounded: `capacity`, default 512, oldest dropped, `dropped` counts them; `capacity: 0` keeps none). The only way out is the caller's own `onCheckpoint` callback. The engine never writes a file, `localStorage`, console output or a request.
- **No asset bytes, no hashes.** No map, tile, picture, sound, string-table or message text, no state-image dump, no digest. See section 4 for what the object-record and cell lists do contain.
- **Copy-safe and stable.** Each checkpoint is a fresh tree of plain numbers, strings, booleans, `null`, arrays and objects that shares nothing with live state and is deep-frozen (a write throws `TypeError` in strict code). `JSON.stringify` / `JSON.parse` round-trips it unchanged. Capturing an unchanged runtime twice gives deeply equal results. `recorder.checkpoints` returns a copy of the buffer array.
- Options: `capacity`, `everyPasses` (record only passes whose counter is a multiple of N, default 1), `onCheckpoint`, `includeObjectRecords` (default true), `includeCells` (default true), `watchCells` (list of `{x, y}`; cells outside the map are ignored).

## 2. Capture boundary (exact)

`MapScene.update(input)` is one 50 Hz video update. In order: frame counter, `Sim.countFrame()` (VBL countdown; pause freezes the decrement but the `$2D` gun latch check still runs, while offers and the build-menu modal freeze the whole timer block), button latches and `MainLoop.vbl()` (modal callbacks count as video updates but do not advance the outer-loop phase or pass count). On a normal pass, `ObjectLayer.update()` advances `$144C9`, own tanks, ships, enemy ground/air and effects; `Sim.pass()` advances the alien/meteor and wave spawner; `animateCells()` then scans visible cells (`$6936`) and snapshots the draw gate. The scene drains previously queued messages, updates message/click timers, and redraws. **Inside that redraw**, between the money and the date text, `Sim.advanceQueuedDay()` models `$4D1C`'s `$564A` tick (the date shown is the post-tick one); **after it**, `Sim.runAfterVblWait()` models `$99C4` (gun A and daily gun B/ship processing, then weekly/monthly/yearly work), and `poll()` models `$50B2`; the checkpoint is captured after the input latches are cleared. The original order `$333A` → `$6936` → `$6540/$3310` → date work → VBL wait → `$99C4` → `$50B2` is static Disk.1 evidence, not a live invasion comparison. The remake still approximates the hardware VBL wait by placing these phases at a configured browser pass boundary. Consequences:

- Normal checkpoints exist only for updates that complete a simulation pass, ordinarily every fourth update with the default `DEFAULT_VBL_PER_PASS = 4`; after a modal interval the first resumed pass is queued for the next update. Modal diagnostic checkpoints are sampled every four modal video updates without advancing the simulation phase. `video.updatesIntoPass` is 0 at those boundaries (it is non-zero only for "manual" captures). The day countdown `$14590` in the checkpoint has already been decremented by the update that completed the pass.
- `boundary` is `"pass-end"` for a normal cycle and `"pass-end-modal"` for a diagnostic sample taken every four browser updates that began in the modal build-menu loop (`controls.menuVisible`: the VBL timer block, simulation, units, `$144C9`, effects and outer-loop phase/pass count are frozen; menu input is polled once per video update and redraw plus separate message/click timers continue). The original `$B3D8` loop calls `$50B2` without a VBL wait; 50 Hz polling is the remake's browser-input approximation. A pass that opens the menu at its own end is still `"pass-end"`.
- `queues.simMessages` / `simEvents` include work from the completed cycle; `simMessages` produced by post-draw `$99C4` have not yet been drained into the message line and appear in `queues.messagesPushed` on the next update (the observer sees them when handled). UI/builder messages from `$50B2` are captured after the input poll; `-1` stands for a pre-patched text line (marker pin message).
- `captureCheckpoint()` (manual) can be taken at any time between updates and has no boundary guarantee; `sequence` is `-1`.
- `Game` consumes `sim.events` after `scene.update()`; a checkpoint taken in `update()` therefore sees the events of the current pass before the shell takes them.

Alignment with the original: the original's pass length is machine and pointer dependent (4 or 5 VBL on Copperline, section 6 of `map-rendering.md`), so align by the observable counters, not by video-frame count: `video.passes`, the `$144C9` sub-tick (`passClock.sub`, with `moveTick` on the pass that wraps to 0 and `enemyTick` on the pass that reaches 4), the date and `$14590`. Static Disk.1 tracing establishes the order of unit/enemy movement, alien/meteor/spawn work and `$99C4` (section 6 of `sim-port.md`); the exact instruction-stop alignment used by a debugger capture still needs to be stated per comparison. The tank and November comparators are bounded to their documented checkpoints. One RAM-staged invasion capture passed its queued, spawned, moving, demolished, gun-kill and after-kill checkpoints; the inconsistent staged baseline and capture provenance limit that result to those states, not ordinary-play combat.

## 4. What the lists contain (privacy and asset note)

Object records, occupied cells and watched cells are runtime state of the player's colony: building tile ids, cell coordinates, counters and occupancy bits. They are derived from the scenario the player loaded but are small scalars copied one by one, never raw buffers, never a map or tile dump, never hashed. `cells` deliberately drops tile ids and terrain flags (only the two occupancy layers and the flag byte); `watchedCells` gives the whole word only for cells the caller names. The checkpoint can still reveal what the player built, so it is kept in memory and handed out only through the caller's own calls.

## 5. Limits

- Not captured: the RNG state (a closure in `Sim`; compare RNG-dependent outcomes, not the generator), `Messages` text, sound/music state, the screen, `Controls` state and open dialogs, the browser input latches (`sawLeft` / `sawRight`), unit and enemy Disk.4 provenance (`sourceRaw`, `sourceAddress`, saved-record pointer fields other than the live enemy slot `+$16` arrays), the 100x75 map and the 7650 flag bytes as a whole, object records that are free (tile word 0), the type table beyond `active` / `total`, and the full state image.
- This note does not define the original-side capture: it does not say what a Copperline / WinUAE debugger script must read, only which remake values correspond to which documented addresses. Byte widths and signedness follow the remake's own readers (`state.ts`, `sim.ts`); a field is only as trustworthy as the note that documents its address.
- Enemy `+$16` pointers are copied raw from their fixed slots, including free slots. `reservation` is only a convenient mirror for a playable cell named by that pointer; zero, padding and out-of-range values yield `null` and remain in `flagPointer`. Tank and ordinary ship reservations remain coordinate-derived; Disk.4-restored `+$14` pointers remain the source of the ship reservation (`ship-control.md` 5c).
- A missile's `target.occupied` is the live slot occupancy at capture time; launched and restored missiles share one shape and resolve their target slot at run time (`ship-control.md` 5c/5d).
- The checkpoint cadence follows the remake's configured pass length (4 VBL). It does not model the original's pointer-dependent 5-VBL passes.
- Experimental Disk.4 scenes capture the same way; the unrestored parts (RNG, lights, `sysFlags`, post-load initialisation) simply read as the remake holds them.
- `test/checkpoint.mjs` pins the snapshot contract and the no-effect guarantee of the remake only; its `MapScene` part needs the local Disk.1/Disk.2 and is skipped without them.

## 6. Original comparison (tank slice, optional, local only)

`test/tank-original-compare.mjs` (in `npm test`; it prints "skipped" and exits 0 unless `UTOPIA_TANK_TRACE_DIR` names the player's own Copperline capture directory, or its parent holding `ledger/`; also skipped without Disk.1/Disk.2). The captures (`cap_NNN_*.json`, disjoint RAM segments `{addr, len, hex}`) stay outside the repository: nothing is copied, hashed or stored, only compared scalars are printed. Evidence: one Copperline 1.0.1 run (sim-port.md "Observed original production, order, and movement"), scenario 0, one own tank.

- **What is staged.** A real `MapScene` on the unmodified scenario-0 map. The remake's own paths do the rest: a yard record (tile `$45`) at (48,49), `UnitSystem.spawnAtYard()` (picks exit 0 = (48,48)), pin 1 at (52,49), `UnitSystem.order()`. The only value taken from a capture is the baseline `$144C9` (the remake cannot know the original's phase). The day countdown is frozen; `$14590`/date are not compared (the original ran 5-VBL passes, the remake runs 4).
- **Checkpoints.** Baseline = `cap_..._order_first_pass_after_exit` (pass 0), then the labels `p006, p014, p022, p030, p038`. Labels are 0-based passes after the baseline (`p001` has `$144C9` = baseline + 1). The comparator derives the offsets from the captures: the chain of consecutive captures between baseline and target must each add 1 to `$144C9` modulo 9 and be 3..6 frames apart (one 4-5 VBL pass each); the offset is then the number of steps. Observed: `$144C9` 3 at the baseline and 0, 8, 7, 6, 5 at p006..p038, i.e. 6, 14, 22, 30, 38 passes, all equal to their labels. Without the full chain the label is accepted only if it agrees with the counter modulo 9 and a 4..5.5 frames-per-pass average. The remake side is read inside `onCheckpoint` (pass-end boundary, section 2), so the map and flag arrays belong to the same instant.
- **Compared, field by field, at every checkpoint.** Per captured tank slot (all 99 at the baseline, slots 0-1 later): occupied/type, x, y, dx, dy, dir, vx, vy, hp, `+9` control byte, tech, target x/y (`+B/+C`), `+$10..+$12`, reservation pointer `+$14`; `$144C9`; `$156A9` bits 7 (move tick) and 6 (enemy tick); marker pins 1-2 (`$14540`); over every captured map/flag slice (about 690-2060 cells): map bit 14, the rest of the map word (excluding the cell (50,51) where the observed run also placed a mine that is not staged) and the flag byte. 6339 fields at the baseline, 2098 at each later checkpoint.
- **Not compared.** Tank bytes `+D`, `+E/+F`, `+13` (not modelled), counters (`$1429C`, `$14254`, `$143B6`), `$14590` and the date, RNG, anything outside the captured slices (map rows and RAM not in the segments), screen/sprites, the production/resource path before the baseline.
- **Result (2026-11-06; rerun 2026-11-07).** Baseline and p006/p014/p022/p030/p038 matched in every compared field on both runs; all six checkpoints reported zero divergences. The earlier p038 divergence was after arrival: the original holds `+B = $FF` but `+C` = 49 (unchanged), while the remake's `arrive` also cleared `+C`. The static `$38E2` trace in units.md section 5 already says only `+B` becomes `$FF`, so `arrive` in `units.ts` now clears `+B` and velocity only (the crusher override already did); `test/tank-lifecycle.mjs` asserts this. The first move (direction chosen, `+9` = `$7F`, velocity (0,2)) lands on the pass where `$144C9` wraps to 0, as the remake's rule predicts from `$144C9` = 3.
- **Second optional comparison (monthly transition).** `test/production-original-compare.mjs` (`UTOPIA_PRODUCTION_TRACE_DIR`) uses the same pass-end checkpoint (`cp.tanks`, `cp.passClock`, `cp.time`) to compare the 28/10 -> 01/11/2090 pass of a separate Copperline run, with a test RNG adapter that checks call order/site/range and computes each result with the isolated original `$2DCC` model (`src/game/original-rng.ts`) from the recorded caller D0, TOD byte and seed, verified against the recorded result/seed (7 of 62 call sites; seed initialiser `$2DA0` untraced; sim-port.md "Original RNG routine model"). Static tracing showed `$144A5` is the low byte of the alien phase word `$144A4`, and `$333A` updates that phase and alien `+$5` once per unpaused pass. The current comparison has a bounded one-run scope; it does not establish broad parity. See sim-port.md "Monthly RNG tape".

It is not an emulator-level comparison and says nothing about other scenarios.

## 7. Invasion original comparison (optional, one RAM-staged capture)

`test/invasion-original-compare.mjs` (`npm run compare:invasion`, not part of `npm test`) replays one bounded ground invasion. The 2026-11-07 capture is RAM-staged, not ordinary play, and the observed baseline has an inconsistent object count relative to its non-empty records; treat this comparison as evidence for the staged states only. The explicit replay passed at queued, spawned, moving, demolished, gun-kill and after-kill checkpoints, with zero divergences in each of the eight groups and all RNG/TOD/raster tape rows consumed (RNG 51/51, TOD 70/70, raster 1/1). This is not broad invasion or combat parity.

**Regression and fix (2026-11-10).** A fresh run of the working tree failed with `FAIL tape replay: RNG draw #6 from randomBuildingRecord, range 2: site random-building ($11A7A) belongs to remake function randomBuilding`; the committed HEAD had passed. The cause was an uncommitted split: the `$11A74` draw had moved into a helper, `randomBuildingRecord()`, while the contract binds the site to `randomBuilding`. The site check rejected the row before its range was compared. The draw now lives only in `Sim.randomBuilding()`, which returns `[x, y, tile]`; the contract binding and the comparator were not changed. Re-verified on the working tree: zero divergences in all six checkpoints (48 groups), with draw #6 matching in range (2), result (1) and site. Static Disk.1 semantics of the draw: `move.w $142C2,d2`, `cmpi.w #$FE,d2 / ble` (signed; the clamp is `$FE`), `ext.l`, `jsr $2DCC` at `$11A74` (return `$11A7A`); the result is `(range * (seed & $FF)) >> 8`, so 0..range-1 and 0 for range 0; the scan `tst.w (a0)` skips `result` used records and returns the next one's +4/+5, with +0 as the tile word; the not-found exit leaves D2 = `$FF`, which the arson (`$10D48`) and meteor (`$1163E`) callers test and the remake reports as `null`. Not exercised by this capture: a range-0 row (the tape validator rejects `range < 1`, while the original would give result 0), and a count word at or above `$8000` (the signed compare keeps the raw word, while the remake clamps to `$FE`; object counts are bounded by 1000 records in ordinary play). Both are left as they are. `test/invasion-lifecycle.mjs` remains the synthetic regression. `test/invasion-contract.mjs` (in `npm test`) validates the provenance schema and address table below with synthetic input; it is a contract test, not an original capture or replay. With `UTOPIA_INVASION_CAPTURE_DIR` unset the comparator prints "skipped" and exits 0. An explicitly empty value is a `configuration` error; a nonexistent directory is a `capture-directory [not-found]` error. Missing or inconsistent capture files are `malformed-capture` errors, while states the remake cannot seed or observe are `unsupported-capture` errors; each exits 1. Nothing from a capture is copied, hashed or stored.

**Capture schema** (`utopia-invasion-capture/1`; the header of the script is authoritative): `manifest.json` includes scenario, required machine fields (`emulator`, `version`, `cpu`, `chipset`, `video`, `chipRamKiB`, `fastRamKiB`), a required `provenance` block (below), seven `checkpoints` in the order `baseline, queued, spawned, moving, demolished, gun-kill, after-kill`, and `passTops`. Each snapshot has `label`, `pass`, `frame`, `spawner {groupIndex, cursor}`, and non-overlapping bounded `segs [{addr, len, hex}]`. Three JSONL tapes carry RNG (`n, pass, frame, site, ret, range, result, seedBefore, seedAfter`), TOD and raster (`n, pass, frame, site, ret, value`); every `ret` must equal the exact address bound to its site label ("Original call/read bindings" below). Required RAM capture coverage in every snapshot (not every captured byte is compared): `$13034..$14633` state image, `$156A8..$156B3`, wave cursor word `$12A94`, `$39D42..$3B466` entity lists, `$3B466..$3D3A6` object records, `$3D3A6..$3F188` flag bytes, `$3F256..$42E1A` map words. Static Disk.1 code `$11912` uses `$156B2` as a byte and `$11898/$1190C` use `$12A94` as a word; each snapshot's self-reported spawner values are checked against those RAM bytes. Machine details are required and printed for run identity, but are not matched to a supported-emulator allowlist or cryptographically tied to the files. Unknown schema fields, overlapping segments and segments outside the capture range are rejected. Checkpoint labels are checked against their local RAM predicates, but they are not proven to be the first pass where each event occurred.

**Provenance (`manifest.provenance`, required; no `/1` capture predates it, so the schema name is unchanged).** Records how the baseline state was reached:

```json
"provenance": { "setup": "ordinary-play" | "ram-staged",
                "stagingWrites": [ { "addr": 85673, "width": 1, "before": 3, "after": 7, "reason": "why this write was needed" } ],
                "noWritesAfterBaseline": true }
```

- `setup` is exactly `"ordinary-play"` or `"ram-staged"`. `ordinary-play` requires `stagingWrites` to be `[]`; `ram-staged` requires at least one write (a staged capture that lists nothing is contradictory and rejected).
- A write is `{addr, width, before, after, reason}`, listed in the order made: `addr` an integer with `addr + width` inside the captured RAM range (`< $43100`), `width` 1, 2 or 4 bytes (big-endian), `before`/`after` unsigned integers that fit the width and differ, `reason` a non-empty string (<= 500 characters). Two writes touching the same byte must chain: the later `before` byte equals the value the earlier write left (the check is per byte, so a byte poke into an earlier long is checked too). Unknown keys are rejected.
- `noWritesAfterBaseline` must be the boolean `true`: nothing may be written to RAM from the baseline pass top to the after-kill pass top. A non-boolean is `malformed-capture`; `false` is `unsupported-capture [writes-after-baseline]` because the replay feeds no input and patches no state.
- What it proves: nothing. It is the capture author's declaration and the comparator can only check its shape and internal consistency. The `after` values are NOT compared with the baseline RAM (the game may run between a staging write and the baseline pass top), and writes cannot be matched against the snapshots. The comparator prints the setup (`ordinary play` or `RAM-staged (N declared pre-baseline write(s), M byte(s))`, both marked self-declared) in the capture identity line and in the final verdict, so a staged run is never reported as ordinary play. Staging is a legitimate way to reach a quiet scenario (see the protocol below) but any result from a staged capture only applies to that staged baseline.

**Original call/read bindings.** Every supported site label is tied to one instruction of the local Disk.1 and to the exact `ret` value a capture tool must record; rows with any other `ret` are `malformed-capture [ret-mismatch]` (the message names the label that owns the address when it belongs to another one), and a label outside the table is `unsupported-capture [unknown-site]`. Addresses come from the static caller audit ([original-rng-callers.md](original-rng-callers.md) section 5, [sim-port.md](sim-port.md) "Original RNG routine model") and were re-read from the Disk.1 bytes; `ret` follows the convention of the November tape (the pushed return address, call + 6: `$9BCC` -> `$9BD2`). Static evidence only; none of these sites has been observed in an invasion run, and the audit's open D0/context rows (original-rng-callers.md section 8) are unchanged.

At start the comparator checks the table against itself (unique return addresses, `$2DCA` sites range 100, `moveq` ranges) and against the player's `Disk.1` (instruction bytes at each address, plus the two `moveq #n,d2`): a different release or a damaged file stops with `original-input [site-binding]`. Labels sharing a remake function (`wave-warning-*`, `wave-group`/`wave-entry`) are now distinguished by address, no longer by order alone; the order and range checks still apply on top. The TOD "return address" is a continuation address, not a pushed one: a debugger watching the access may stop at a different PC, so a capture tool must map its stop to `$1269A`. `$B056` and `$11786` read `$144CA` through `ext.w`/`subq.b` (family E, premise P2 in the audit), `$11762` follows `bsr $B018` (UNRESOLVED D0 byte 1 in the audit); those D0 caveats concern the D0 input of the original routine model, not the address binding.

**Timing.** The original's pass length (4 or 5 VBL, `map-rendering.md` section 6) is not assumed to equal the remake's 4. `passTops` lists every original pass top (`$157BC`) with its VBL frame; the replay runs the pass starting at top *t* with `frame[t+1] - frame[t]` `MapScene.update()` calls, so `$14590` and the `$2D` latch see the original VBL count; the pass work still runs on the last update of that interval, so alignment is exact only at pass-top granularity (the original interleaves VBL ticks with pass work; `$14590`, `$144C1` and the latch outcome are compared as the check). The scene is built with `vblPerPass` = the longest recorded pass and `MainLoop.restoreAt` sets the phase inside each interval (scheduler only, no game state; `video.updates` of the checkpoints is therefore not meaningful here). A remake pass-end checkpoint corresponds to the original's next pass top.

**Replay.** One real `MapScene` is seeded from the baseline (state image, object records, all 100x75 map words and 75x102 flag bytes verbatim, `$156AA`, `$156A8` bit 7, `$144C9`, spawner via `Aliens.restoreSpawner`, view from `$144E4/$144E6`, and the raw `+$16` long of all 60 + 30 fixed enemy slots, free ones included). A seed read-back against the baseline must match or the run stops with `unsupported-capture [seed]`. Then it runs continuously: no reseeding, no combat-method override, no patched state. Captured RNG results, TOD and raster values are injected through `SimOptions.rng` / `.hardware` and checked for site-label/function, range, tape order and pass; after each pass, consumed rows must match the capture. **This does not validate the remake's PRNG implementation against captured seed transitions** (the result is injected), nor does it compare the exact VBL offset of an individual read within a pass. The capture validates seed-chain formatting/continuity and original pass boundaries only. The first divergence stops the run.

**Compared at each checkpoint** (existing checkpoint fields): timing (`$14590`, `$144C9`, mapped bits of `$156A8/$156A9`, `$156AA`, tick bits, `$144C1`, date and event index); spawner byte/word and every queue long; occupied ground enemy fields plus occupancy and the raw `+$16` pointer of every ground/air slot; enemy counts and 32-bit kills `$14298`; own tank/ship counts and baseline emptiness; all 1000 object records (demolition, gun `+6/+7` timer, `$142C2`, `$142C4`); the 30 effect slots (the count word `$156AE`, then per slot occupancy and, for an occupied one, type, cell, frame and lift, slot for slot, holes included); all 100x75 playable map words (bits 14/13 and remainder) and all 75x102 flag bytes including padding columns; the view; and a residual sweep of every other state-image byte (excluded: `$14590` compared above, date text `$14594..$1459D`, `$144C9`, `$144E4..$144E7`). Map padding words at x=100/101 are not part of the remake's packed `World.cells` and are not compared. Unoccupied enemy record tails and unmodeled bytes in the separate entity-list headers are not compared.

**Known gaps (fail or documented, never silently dropped).**
- Own tanks/ships/missiles in any snapshot, an enemy aircraft, a non-empty enemy list, queue or effect list at the baseline: `unsupported-capture` (no seeding path outside Disk.4 adoption; this slice is ground-only and starts quiet).
- Effect slots: the static trace gives 30 fixed 8-byte slots with first-free allocation and slot-local expiry; the comparator reads `$156AE` as a WORD, inspects every slot at `$39D4A` (stride 8), validates that the count equals the number of occupied slots (type byte non-zero; otherwise malformed capture), accepts holes and compares occupancy plus type, cell, `+5` frame and `+6` lift slot for slot. An occupied slot with a non-zero `+3/+4/+7` byte is `unsupported-capture` (the remake `Effect` has no such fields); a free slot's other bytes are not compared. A non-empty effect pool at the BASELINE is still `unsupported-capture`: the slot layout is known, but no seeding path into `ObjectLayer.pool` exists in the scaffold. The `$1237C` descriptor clobber at `$149C` is not observed.
- Spawner encoding: statically verified in the local Disk.1 code: `$156B2` group index is accessed as a byte at `$11912`; `$12A94` cursor is loaded and stored as a word at `$11898/$1190C`. Capture values are checked against those RAM locations. The supported state range (group 0..15, cursor 0..$80 in multiples of 4) is a comparator policy based on the observed/ported queue representation, not a claim that every other original value is impossible.
- RNG sites: only the sites in the script table (intel countdown, wave warning, wave group/entry, random building, enemy bomb chance) are known; any other draw in the window (other daily events, alien/meteor rolls) is `unsupported-capture [unknown-site]` until its traced mapping is added (the other 55 of the 62 audited sites have static addresses but no label here). The invasion call sites ARE documented (original-rng-callers.md section 5) and are hard-coded in the table above; the capture tool must record those exact return addresses.
- Capture `ret` is checked for equality with the address bound to its label (table above; derived from the static audit and the local Disk.1 bytes, not from an observed invasion run). `seedBefore/seedAfter` and `frame` values are capture-integrity metadata. RNG seeds are checked for formatting and chain continuity; because results are injected, this does not verify the remake's `$2DCC` PRNG algorithm. Tape frames are checked to be monotonic and within their recorded pass, but individual reads are not aligned to exact VBLs inside that pass. The comparator does not reproduce hardware TOD/raster reads, bind capture files to a machine fingerprint, or verify the `provenance` declaration against the files.
- Only mapped bits of `$156A8/$156A9`, whole `$156AA`, the spawner fields, and `$156AE` are compared. `$156A9` bit 5 (the blast mark, `time.blastMark`) is captured but not compared yet: the static trace (ship-control.md 5e) implies that at a pass boundary an original snapshot's bit 5 equals the mark, so a future comparison can use it, but no capture has checked that. Other `$156A8..$156B3` bits/bytes are capture-covered but unmodeled and un-compared. The effect count is read as a word at `$156AE` and cross-checked against the occupied slots.
- The occupied ground record fields are mapped; empty-record tails, air `+$11/+12`, own tank/ship record arrays (the baseline requires them empty), unmodeled list-header bytes, and the non-type bytes of free effect slots are not compared. The comparator still checks relevant counters, all enemy slot pointers, all 30 effect slots, objects, playable map words and flags; this is a bounded comparison, not a whole-RAM or general parity result.
- Not compared: warning lights, message text/log, sound, screen, Disk.4-style provenance, `World` solar-phase stream (a built solar tile reads the beam through its own stream, not the tape), TOD/raster real hardware timing (tape values are replayed, not reproduced). If the remake opens an Earth offer, that is reported as a comparison divergence.
- Cell animation is compared as part of the map-word remainder; the remake animates only the view window and its position inside `$333A` is untraced, so an animated cell in view may surface as a divergence of its own.

**Smallest original capture protocol** (WinUAE/Copperline, disposable WHDLoad tree, one scenario, RAM staging allowed but to be declared in `manifest.provenance`: `setup`, every pre-baseline write with address/width/before/after/reason, and `noWritesAfterBaseline: true`): (1) stage a quiet colony: no own tank/ship, no effects, empty wave queue, exactly one queued-entry-sized wave (one ground walker), one active target building, one finished Gun A with a clear arc and Gun A damage able to kill the walker, `$14590` known; (2) from the baseline pass top until one pass after the gun kill, log a pass counter and the VBL frame at every `$157BC` hit (`passTops`); (3) log every `$2DCC` call (return address, `d2`, result, seeds, frame), every `$BFE801` read of `$1266A` (value, frame) and every `$2E00` result used by the wave launch (parity, frame), each stamped with the current pass counter, recording the pushed return address of each call (for the TOD read the address after the `move.b $BFE801,d1` at `$12694`) and labelling it with the address table above; (4) at the seven pass tops (baseline; first queued entry; one enemy; changed `+$16`; fewer object records; kill counter +1; the next pass) dump the six RAM areas above plus the spawner scalars.
