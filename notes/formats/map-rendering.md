# World map rendering (static analysis of the game proper)

How the original draws the isometric world view in gameplay mode (`$14591 = 1`). Addresses refer to the game image (Disk.1 sectors $14C-$208 at $1000, "variant A"), see `game-proper.md` for the surrounding structure. No game graphics are reproduced here, only addresses, layouts and numbers. Helper tools: `tools/map_common.py` (loaders), `tools/map_render.py` (renders a view of any scenario to a PNG using the formulas below; this is how the projection was checked visually), `tools/map_verify.py` (asserts the formulas against the tables inside the game image).

Tags: **VERIFIED** = read from disassembly/data and cross-checked (by script or by a coherent rendering); **HYPOTHESIS** = inference.

## 1. Summary (VERIFIED)

- The map view is a fixed **8 x 8 cell window** of the 100 x 75 map, drawn as a **diamond** (2:1 isometric). Tile images are **32 pixels wide**, flat ground tiles are 15 rows high, buildings/rocks up to 30 rows, bottom-aligned on the cell.
- Everything is drawn by the **CPU** (no blitter registers are touched anywhere in the map code) into the back buffer of a double-buffered 320 x 200, 5-plane screen; each main-loop iteration redraws all 64 cells and all visible moving objects.
- The 6th plane of a tile image is a **mask** (1 = opaque). Image rows are stored **bottom row first**.
- The scroll position is a pair of cell indices, x 0..92 and y 0..67 (inclusive), top cell of the diamond = map cell (scrollX, scrollY).
- In-game palette = the 32 colour words at the end of the unpacked main-screen background picture.

## 2. Per-frame sequence (VERIFIED)

Main loop `$157BC` (see `game-proper.md` section 3), only the drawing-relevant calls:

| Call | Purpose |
|---|---|
| `$333A` | Builds the **draw list** of moving objects at `$2954A` (12-byte entries, sorted descending by cell order index, terminated by $FFFF) and runs per-object update hooks. Also advances the slow-tick counter `$144C9` (0..8; bit 6 of `$156A9` at 4, bit 7 at wrap). |
| `$16012` | Restores the background of the map window and top bar into the back buffer (section 9). |
| `$6936` | Computes the map pointer for the current scroll in a6, animates map cells (section 7). |
| `$6540` | **Draws the 64 tiles in back-to-front order and interleaves the objects.** |
| `$3310` | Draws the 8 user marker pins on top of everything (section 8.5). |
| `$4D48`, `$4D1C`, `$4D96` | Text in the top bar: money (x 110, y 2), date (x 8, y 2), a second counter (x 224, y 2). Not map related. |
| `$5D30` | Draws small overlay images from a 4-entry table at `$15628` (not analysed). |
| `$4E08` (called after the VBL flag clear at `$15838`) | Swaps the two screen blocks (`$160F2`, `$1610E`), loads COP1LC. Drawing goes to the block whose plane pointers are at `$16116` (5 longs). |

The mouse pointer is software drawn into the displayed buffer (`$2F5E`/`$2FBA`, background saved at `$42F88`), clamped to x 0..$138, y 0..$C0 in **bitmap pixel coordinates** (hot spot = top-left of the pointer image). All hit tests below use these coordinates.

## 3. Scroll state (VERIFIED)

| Address | Meaning |
|---|---|
| `$144E4` word | scroll X (cell column of the diamond's top cell), 0..$5C (92) |
| `$144E6` word | scroll Y (cell row), 0..$43 (67) |
| `$144E8`, `$144EA` words | stored alternate position; new game default is the same as the current one |

- Limits: `$15A28` clamps x to 0..$5C and y to 0..$43 (so the window never leaves the 100 x 75 area; 92 + 7 = 99, 67 + 7 = 74).
- New game (init at `$866E`): both pairs are set to x = $2F (47), y = $21 (33). Whether loading a save or other paths override this was not traced (HYPOTHESIS that saves store the pair in the block `$14234...`).
- **Scrolling is only by the mouse; there are no cursor-key or screen-edge scroll rules.** `$15A28` (d2 = direction, d3 = step) is called from `$15966` (left button, step 1) and `$15F5E` (right button, step 6). Four diamond-shaped arrow buttons, hit rectangles `{x0,x1,y0,y1}` inclusive at `$5DAA`:

| d2 | Rectangle | Effect on scroll | Screen direction of the move |
|---|---|---|---|
| 0 | x 240-261, y 122-132 | y - step | up-right |
| 1 | x 216-237, y 122-132 | x - step | up-left |
| 2 | x 216-237, y 136-146 | y + step | down-left |
| 3 | x 240-261, y 136-146 | x + step | down-right |

- Holding the left button on an arrow repeats the scroll once per main-loop pass (`$50B2` keeps returning "clicked" while bit 0 of `$156A9` is set, and `$15966` sets it). A normal map click acts only on the press.
- **OBSERVED (Copperline run, x+ arrow only, see "Main-loop timing")**: `$50B2` polls CIA-A PRA bit 6 once per pass; a press shorter than the poll gap was lost; a single click spanning one poll scrolled exactly once (47 -> 48); a held button scrolled at **every** poll, the first poll immediately (no initial delay, no acceleration), e.g. 8 polls -> x 47 -> 55. The remake's `MapScene` polls once per pass and has no repeat delay (the old `REPEAT_FRAMES` is gone). The other three arrows, right-click step 6 and bookmark swap were not measured in the original.
- Rectangle x 16-31, y 139-155 (`$5D70`, handled at `$159CE`) swaps the current scroll pair with the stored pair at `$144E8` (a "jump back" bookmark).
- The overview-map click path (`$F2D4-$F2E0`) subtracts 8 and 4 in 16-bit words around a logical right shift. `$FB1E` then signed-clamps x to 0..$5C and y to 0..$43. A click in the top/left 8-pixel margin underflows to a positive word and clamps to the far edge. The port preserves this arithmetic in `scrollForClick()`; `test/overview.mjs` checks both normal centering and the underflow edge.
- Keys 1-8 (`$3202`) place one of 8 marker pins at the selected cell; key `$22` (`$31CC`) clears all pins (section 8.5).

## 4. Projection (VERIFIED)

View cells (vx, vy), vx, vy in 0..7, map cell = (scrollX + vx, scrollY + vy). Top vertex of the diamond = view (0,0); right corner = (7,0); left corner = (0,7); bottom = (7,7).

```
anchorX(vx,vy) = 112 + 16 * (vx - vy)      // left edge of the 32-pixel-wide image
anchorY(vx,vy) =  39 +  8 * (vx + vy)      // the row just BELOW the image's bottom row
image rows occupy y = anchorY - rows ... anchorY - 1     (rows = descriptor rows-1 + 1, max 30)
cell box (used for hit tests and objects): x0 = anchorX, y0 = anchorY - 15 (= 24 + 8*(vx+vy)), size 32 x 15
```

These formulas reproduce all 64 entries of the draw table at `$7828` exactly (12 bytes per entry: word map byte offset = 2 * (vy*102 + vx), word screen byte offset = anchorY*40 + anchorX/8, then four words giving the table-entry distance in bytes to the neighbour cells (vx+1,vy-1), (vx+1,vy), (vx,vy+1), (vx+1,vy+1), 0 when that neighbour is outside the 8 x 8 window). Screen byte offsets assume 40 bytes per row; anchorX is always a multiple of 16, so the CPU blit works with word-aligned longs.

Drawing order (the order of table `$7828`): diagonals by `vx + vy` ascending (0..14), inside a diagonal by `vx` ascending. The ordinal of a cell in that sequence is `seq` (0..63); the object code uses `order = 63 - seq` (tables `$7B28`: cell id word `vx << 8 | vy`; `$7BA8`: `order` at index `vx + 8*vy`).

The window covers x 0..255 (cell boxes) and y 24..~158. Tall images extend above the anchor, so the top of the diamond can draw into the top bar rows (the top bar background is restored *before* tiles, then text on top). The right clip for objects is a per-pixel rule that depends on the sprite's left edge (section 7.3).

Pseudocode (map `m` = 100 x 75 array of 16-bit words, stride 102 in memory but a 2-D array in a remake):

```ts
for (let s = 0; s <= 14; s++)
  for (let vx = Math.max(0, s - 7); vx <= Math.min(7, s); vx++) {
    const vy = s - vx;
    const order = 63 - seqOf(vx, vy);
    drawTile(map[scrollY + vy][scrollX + vx], 112 + 16*(vx - vy), 39 + 8*(vx + vy));
    drawObjectsWithOrder(order);          // section 8
  }
drawMarkers();                            // section 8.5
```

## 5. Tile images and the blit (VERIFIED)

- Cell word: low 10 bits = tile id, high 6 bits = flags. **Descriptor index = (word & $3FF) - 1** (`$6588`: `subq #1`, `andi #$3FF`, `lsl #3`); id 0 would give index $3FF (outside the table; no map in the data set contains id 0 or 1 below 2, ids seen in all 10 scenarios: 2..161).
- **Ids are 1-based, so id 161 is valid** (VERIFIED over all 10 scenarios with `tools/map_common.py`): the maximum id is 161 and there are no ids above 161 and no id 0. Id 161 maps to descriptor index 160, the last of the 161 entries (0-160). The 1,200-1,600 cells per scenario with id 161 are the fourth flat ground variant (ids 158-161 are four flat ground images that make up 4,800-6,650 cells per scenario). There is no remap, object or special value involved in these ids; an implementation that indexes the table with the raw id (no `- 1`) goes one past the end for id 161 and shifts every tile by one. Ids 1-13 are the animated building ids of section 6, the border pad value $73FF (id $3FF) never appears inside the 100 x 75 area and is never drawn because the scroll limits keep the window inside it.
- Descriptor table: pointer in `$1612E`, 8-byte entries `{long rows-1, long absolute data address}`, 161 entries. Entries 0-94 come from the Disk.1 tile sheet (offsets relative to sheet + $508, relocated by `$7C62`), entries 95-160 from the scenario's graphics (relocated at `$7CA6`: offset + (`$1612E` + $CA00)). Map ids 96-161 therefore select scenario-specific images (ids 98-161 are terrain: rocks and craters with blocked flag, and four flat ground variants 158-161); ids 1-95 are shared buildings and base parts.
- Image data (per image): `rows` rows of 4 bytes (32 pixels) per plane, planes 0..4 one after the other, then the **mask plane** (6th) = `24 * rows` bytes total. **Rows are stored bottom row first** (the unrolled blitter reads the data backwards while writing the screen top-down).
- Blit routine `$6540` (base tile at `$655E`-`$65D6`): for each of the 5 bit-planes it calls a 30-group unrolled routine at `$6754` (16 bytes per group, one row per group: `dst = (dst & ~mask) | (src & mask)` on one 32-bit long, destination row stride 40 bytes). The entry address is `$6754 + (30 - rows) * 16`, so any height up to 30 rows works; destination = plane pointer + `anchorY*40 + anchorX/8` - 1200. Plane order in the loop is 4 down to 0 (irrelevant for the result).
- Mask polarity: bit 1 = image pixel is drawn; 0 = destination kept.
- The cursor/selection tile: when the cell equals the selected view cell (word `$14636` = `vx << 8 | vy`, -1 = none), `$6568` compares the cell key, `$6570` toggles bit 1 of `$156A9`, and when the old bit was zero `$657A` draws descriptor index 58 (`$1D0 / 8`) instead of the map tile. The loaded image has bit 1 set, so the first matching draw uses the normal map tile; this initial phase is now represented in `MapScene`. This is a static-trace-backed alternating tile substitution; no running-original visual comparison establishes its apparent blink rate.
- Large (2 x 2) buildings are just four neighbouring map ids. Ids $48-$5F are 24 ids = 6 buildings x 4 parts; table `$77C8` (2 words per id: type word, footprint offset word with 0, $100, 1, $101 for the parts) is used only by the building-record builder `$6D78` and the overview map `$F41E`, **not** by drawing. The same ids are drawn as a composite of 4 images by `$6A22`/`$69D8` for user-interface previews (x/y given are the bottom row; `$69D8` blits upward from the bottom row).
- Verified by rendering: with these rules the tile images fit the diamond pad of the main-screen picture exactly and tall rocks/buildings overlap correctly for all 5 graphics sets (`tools/map_render.py`).

### Cell flags (high 6 bits)

- Bit 10 ($0400): "animated cell". The only flag the drawing code looks at (section 7).
- Bits 11, 14, 15 are preserved by the tile writers (`andi #$E800`).
- Data observation (scenario 0, 3): bit 12 ($1000) is set on all rock/crater ids and on building ids, together with the border pad value $73FF: **HYPOTHESIS: blocked/occupied terrain.** The path finder at `$3A00` tests bit 12 and uses bit 14 (`bset #6` of the high byte) as a visited marker (VERIFIED code, interpretation HYPOTHESIS). Bit 11 and bit 15 occur on ground tiles (meaning unknown, possibly resource/ownership markers); bit 13 not seen in the data.

## 6. Animation of map cells, `$6936` (VERIFIED code; timing OBSERVED on Copperline only, see below)

Runs once per main-loop pass, for each of the 64 window cells whose flag bit 10 is set (also sets bit 3 of `$156A9`, "needs redraw"):

- id 1..3: id + 1, wrapping 4 -> 1 (3-frame loop; ids 0, 4, 5 not animated).
- ids 6..13, only while byte `$144C8 < 4`: id + 1; if the result is 10 or > 13 then id - 4 (two 4-frame loops: 6-9 and 10-13).
- other ids: unchanged. The low byte of the map cell is rewritten in place, so the animation state lives in the map.
- Because it runs per pass, the animation speed equals the main-loop speed. **OBSERVED** (Copperline, scenario 0, two animated cells (57,37) ids 8,9,6,7,8 and (59,40) ids 3,1,2,3): exactly one step per pass, every pass, 24 consecutive passes without a skipped or extra step. The remake runs `animateCells()` once per `MainLoop` pass (4 video updates by default, i.e. 12.5 steps/s), replacing the earlier guess of 6 frames.
- Meaning of `$144C8` (set at `$A17E`/`$A1B6`, compared in several places) not determined.

### Main-loop timing (OBSERVED, Copperline 1.0.1; limits stated)

Direct observations, not universal claims: Copperline 1.0.1, A1200 profile, 68020, AGA PAL, 1536K chip + 4M fast, scenario 0 (WHDLoad 1.2 files), game pointer drawn in software. Source: a private observation ledger (not in the repo); numbers below are what it recorded.

| Item | Observation |
|---|---|
| Pass length | `$333A` once per pass. Pointer at (175,41) and (60,100): **4 VBL per pass** (74/74 passes, 12.48 passes/s). Pointer on the arrow cluster (250,141), (228,141), (250,128), (310,185): **5 VBL** (9.98 passes/s). Other positions (150,60) 4, (250,100) 4, (280,70) and (100,150) alternating 5/4. |
| Why | **INFERENCE**: CPU-bound. Pass work is ~3.65 frames; the loop then spins in `$2E10` until line 242 of the next frame (VHPOSR high byte $F2) and the VBL-flag wait at `$15846` adds ~nothing. The pass length is therefore machine and pointer dependent, not a fixed limiter. |
| `$144C9` | +1 per pass (0..8, wraps 8 -> 0), also **while paused**. `$156A9` bit 6 set in the pass reading 4, bit 7 in the pass reading 0; cleared by the next pass. |
| `$14590` | -1 per VBL (90-VBL day period, wrap through 0 to 89); **frozen while paused**, resumes from its frozen value. |
| Day tick | `$564A` is called every pass; only the call with `$156A8` bit 7 set ticks the date. So the date changes on a pass boundary after the VBL countdown ran out (pass-quantised: 88-92 frames between ticks). The `$4D1C` caller has no pause guard: a previously queued day still advances the calendar while paused, while `$99C4` leaves its daily/weekly/monthly work pending until resume. |
| Input | `$50B2` polls the left button once per pass, at the end of the pass; scroll arrows: see section 3. |
| Start view | scenario 0 new game: `$144E4/$144E6` = (47,33), bookmark (47,33). |

Remake configuration (`src/game/main-loop.ts`, `MapScene`): `DEFAULT_VBL_PER_PASS = 4`, the measured baseline at (175,41). During normal map operation the scheduler counts 50 Hz video updates and signals a pass every 4th update; `MapSceneOptions.vblPerPass` overrides it. Fresh entry and modal return run one immediate pass before the next VBL-side work; that following VBL counts toward the next interval. The outer-loop phase freezes during the build-menu modal interval, while total video updates continue, and the first pass after exit runs on the next browser update. **Not modelled**: the pointer-dependent 5-VBL passes and the 5/4 alternation (no arbitrary pointer-coordinate exceptions are coded). **Not measured**: WinUAE, other CPU speeds / `cpu_speed=max`, NTSC, other chipsets, other scenarios, the other three scroll arrows, right-click step 6, bookmark swap, overview map. Pass rate is machine dependent in the original, so this is Copperline-like pacing, not emulator-wide fidelity.

Per video update (VBL) the remake runs `Sim.countFrame(modal)`: `$14590` is frozen while paused, an offer is pending, or the build menu is open; otherwise it decrements, queues a day on reload, and latches gun A's special bit at `$2D`. The equality check remains active during pause. Message/click timers continue at video-update cadence. Static Disk.1 caller order is `$157CA` `$333A` (object/special updates and spawn), `$157D4` `$6936` (visible-cell scan/animation and additional redraw-gate sources), `$157DA/$157E0` `$6540/$3310` (map/object draw), `$157E6/$157EC` `$4D48/$4D1C` (date work), VBL wait, `$99C4` periodic work, then `$50B2` input. The remake now runs `ObjectLayer.update()` and `Sim.pass()` before `animateCells()` (`$6936`), snapshots the gate, draws into the alternate persistent pixel buffer, runs the queued day tick `$564A` inside the top-bar draw (`$4D1C` calls it FIRST and then draws the date string, VERIFIED by disassembly `$4D1C`/`$564A`: money `$4D48` is drawn before the tick, the date after it, so the date of the pass whose tick fires is already the new one), runs `$99C4`, then polls input. This relative ordering is static-trace-backed, not frame-compared. The build-menu routine `$B3D8` calls `$50B2` repeatedly without a VBL wait and does not return to `$157BC/$333A` until exit; the remake therefore polls its modal input once per video update (50 Hz) while freezing simulation, countdown and entity movement. The original's tight-loop latency is not reproduced. After the handler returns, the outer loop branches from `$158C6` to `$157BC` with no intervening VBL wait. The remake still counts video updates during its modal polling, but freezes the outer-loop scheduler phase; when the menu closes it queues the next simulation pass for the next browser update. That immediate callback models the observed return to `$157BC`, while exact CPU/VBL timing in the original remains machine-dependent. Normal map redraws now occur only on scheduled passes; modal controls draw over the displayed bitmap into the screen only, without swapping and without writing the persistent bitmaps back (static `$B680`: `$5A16` copies the displayed bitmap to the other one and the panel goes into the back bitmap; exit `$B628`: command buttons redrawn there, `$4E08` swap, VBL wait, `$5A16` copy again, so both bitmaps end as the pre-menu frame; the remake shows the pre-menu frame on the exit update and the next update runs the queued pass). Deliberate browser deviation: a mouse press that began and ended between two polls is latched and seen once at the next poll (the original lost such presses under input injection; the pointer position used is the one at the poll).

Opt-in runtime checkpoints (`MapScene.enableCheckpoints()`, `src/game/checkpoint.ts`, [runtime-checkpoints.md](runtime-checkpoints.md)) copy the state described here after each completed normal cycle: redraw, date advancement, periodic worker, and input poll. They are read-only, opt-in, in-memory and contain no asset bytes; they carry the remake's pass cadence (4 VBL) and add no observation of the original.

Pause behavior (static Disk.1 trace): `$333A` tests `$156A9` bit 2 before tank movement/weapon fire (`$3394`), ship movement/fire (`$3414`), enemy-ground movement (`$34A6`), enemy-air movement (`$350E`), and effect countdown (`$3574`). `$35D2` also gates the alien animation phase, and `$1187C` has its own pause guard before consuming a queued wave entry. The port freezes those entities and spawns while continuing the pass clock and visible map-cell animation. The meteor path has a separate apparent pause loop: `$3638` branches back to `$35FE` while the meteor is live and pause is set, then the draw path returns to `$3626`; the remake deliberately does not reproduce this apparent hang. No live-original pause capture has exercised moving units or an active meteor. `$4D1C` calls `$564A` without a pause guard: whenever a day is queued when that call occurs, the date advances even if paused. `$99C4` returns while paused, leaving the period work created by that date change pending until resume. `Sim.advanceQueuedDay()` and the paused `MapScene` regression in `test/map-loop.mjs` match those rules. The exact coincidence of timer expiry and pause input has no live-original capture: the engine counts each VBL in its video-update callback and polls input at pass boundaries, so no dynamic same-boundary equivalence is claimed. Exact video-frame alignment and a live original firing-cycle comparison remain outstanding.

## 7. Moving objects over the map (VERIFIED structure, field meanings partly HYPOTHESIS)

### 7.1 The 8-byte records of `$6D78` are not drawn

The records at `$3B466` (built from the map by `$6D78`: type word, bytes, x, y, rand) are **building/game-logic records**. Buildings appear on screen only through their map tile ids (section 5). Only objects in the arrays below are drawn as sprites.

### 7.2 Object arrays and the draw list

`$333A` walks several arrays (the first byte of an entry = type, 0 = free slot) and, via `$3694`, turns each visible entry into a draw-list entry `{word order, word y, word x, long entry address, word flags}` (12 bytes) at `$2954A`:

| Array | Stride | Count variable | Flags in draw list | Notes |
|---|---|---|---|---|
| `$3AB06` | $18 | `$1429C` (max 99) | 1 | units/vehicles; neighbour redraw applies (8.2) |
| `$3A746` | $18 | `$1429E` | 0 | uses lift byte +$10 |
| `$3A12C` | $1A | `$142A2` (max 60) | 3 | |
| `$39E20` | $1A | `$142A4` (max 30) | 2 | uses lift byte +$10 |
| `$39D42` (entries from `$39D4A`) | 8 | `$156AE` (a word) | 0 | short-lived effects: 30 FIXED slots, a new one takes the first free slot, byte +5 counts down and frees only its own slot below 0; lift byte +6 (units.md section 6) |
| `$144A8`, `$1449C` | single | - | 0 | alien (inserted first) and meteor special effects; meteor bytes end at `$144A3`, and `$144A4..$144A5` are the alien frame-phase word |

Common entry layout: +0 type (index into the sprite descriptor table, 1-based), +1 map x, +2 map y, +3 signed byte pixel dx, +4 signed byte pixel dy, +5 frame/direction index. `$3694` returns **screen position = (pick-table x0 + dx, pick-table y1 + dy)** for the object's cell where `x0 = 112 + 16*(vx-vy)` and `y1 = y0 + 14 = 38 + 8*(vx+vy)` (the bottom row of the cell box), minus the lift byte for some arrays. The object is skipped when its cell is outside the 8 x 8 window; a few extra rules for cells in the last column/row (vx = 7 or vy = 7) hide objects that are moving out of the window depending on type (types $12/$14 are always shown) and the sign of dx/dy (code at `$36D4`-`$3732`).

The transient word `$142A0` is cleared at `$337C`, incremented once for each admitted visible original entry during `$333A`, then read by `$3680` and passed to the `$4860` sort. It is the current draw-list length, not an object-record count; remake-only `ObjectLayer.extra` entries are excluded. The pass stores this count after movement and spawn, before the next redraw. A RAM-staged invasion comparison initially diverged at this word; after modeling it and the enemy bomb-coordinate words (enemies.md section 6), the explicit seven-checkpoint replay reported zero differences in every compared group. The capture is RAM-staged and does not establish ordinary-play invasion parity.

For the alien record at `$144A8`, `$333A` advances word `$144A4` once per unpaused pass while the type byte is nonzero, then copies `$11718[index]` into `+$5` (`$144AD`). The table is `00 01 02 03 02 03 02 03 02 01 00` and index 11 wraps to zero. This runs before `$3694` decides whether the alien is on-screen, so visibility does not gate animation. `$144A5` is the low byte of `$144A4`; it is not a meteor field. This animation-state trace is static, and the four November pass snapshots corroborate its values. Runtime sprite artwork and its visual parity are separate questions.

**Alien apparition drawing in the remake (`src/game/alien-sprite.ts`, `ObjectLayer.apparition`).** The active type-19 record is drawn through a read-only adapter: `readAlienApparition(state)` reads only `$144A8..$144AD` (type `$13`, x, y, signed `+3`/`+4`, frame `+5`) and returns a drawable; `MapScene` installs it as `objects.apparition`, and `ObjectLayer.drawMap` (`FramePass.drawAfterCell`) blits it with the existing `SpriteSet` frame decoder, bottom-row anchor `anchorY - 1 + dy - 13` (the type-19 insertion block at `$3604` subtracts 13 from the y anchor after `$3694`; only the alien takes this adjustment), and left edge `anchorX + dx`. `$3694` sign-extends `+3`/`+4` and adds them to the pick-table pixel anchors. For the active alien frames 0..3, at the last column frame 0 always passes; frames 1..3 are hidden when either offset is positive. At the last row frames 0..2 pass regardless of offsets; frame 3 is hidden when `dy > 0`. These conditions are statically traced; `ObjectLayer.shown` applies them through the shared rule using `+5` as its selector. The blit uses the same `x < 0 || x >= 256` rejection and shared per-pixel right clip of section 7.3. Drawing does not write the record, advance `$144A4` / the frame, touch RNG, occupancy or effect slots. The alien is an admitted draw-list entry that sorts, never opens the redraw gate and is an obstacle (not an order target) in `pickables` (section 7.2b). A type byte other than `$13` or a frame byte above 8 draws nothing. The record/anchor/edge behavior is VERIFIED by static Disk.1 tracing; the port's new-game path writes zero offsets, while restored state may supply them. Artwork and palette parity with the running original remain unverified. Checked by `test/alien-sprite.mjs` (synthetic and local-data wiring checks; no original pixel comparison).

**Meteor drawing in the remake (`src/game/meteor-sprite.ts`, `ObjectLayer.meteor`).** The active type-21 record at `$1449C` is drawn through a second read-only adapter of the same shape: `readMeteor(state)` reads only `$1449C..$144A2` and returns a drawable, `MapScene` installs it as `objects.meteor` (polled at draw time, never stored, never written through; an admitted draw-list entry that sorts and, in `pickables`, is an obstacle but never an order target, 7.2b), and `ObjectLayer.drawMap` (`FramePass.drawAfterCell`) blits it with the existing `SpriteSet` frame decoder, the shared per-pixel right clip of section 7.3 and the window-edge rule. Record, from a read-only static trace of Disk.1 (no emulator comparison): `+0` type `$15`, `+1`/`+2` map x/y, `+3`/`+4` signed pixel dx/dy, `+5` descriptor frame index, `+6` one signed byte that is both the countdown (`$3626`: -4 per unpaused pass, impact at 0; `Aliens.meteorStep`) and the drawing lift, `+7` not read by the inspected draw path. ### 7.2b Draw list: insertion order, order keys, the `$4860` sort and picking (static trace of the local Disk.1 image)

**Insertion order** (`$333A`): own tanks (flags 1), own ships and missiles (0), enemy ground (3), enemy air (2), the effect slots in ascending slot order (0), the alien (0), the meteor (0). Holes are skipped. Each entry keeps its flags, its source and its record; the screen placement is `$3694`'s. `$3694` visibility admission happens BEFORE the sort; a later blit rejection (left edge x < 0 or >= 256) or a sprite with no pixels does not remove an entry from the sort (it still blocks in the pick scan). `src/game/objects.ts` `admitted()` is that step (`kind` per entry); the remake's untagged `ObjectLayer.extra` drawables are NOT part of the original list: they are appended last with flags 0 as an explicit approximation, are not saved and are pickable only with a `ref`.

**Order key.** `$7BA8[2 * (vx + 8 * vy)] = 63 - painterSeq` of the entry's view cell; the 64 keys are unique (`draw-list.ts` `orderKey`, `PAINTER_CELLS`).

**The sort `$4860`.** For `end` from n - 1 down to 1: `selected = 0`; for `scan` = 1..`end`: when `entries[selected].order >= entries[scan].order`, `selected = scan`; then, inside EVERY inner iteration, `selected` and `end` are exchanged when they differ (the index `selected` stays; it now holds what was at `end`). The result is globally descending by order key, but equal keys (several entries on one cell, or any ties) are NOT kept in insertion order: three equal entries a, b, c end as a, c, b, four as a, b, d, c, five as x0, x4, x2, x1, x3. It is ported literally as `sortDrawList` (no `Array.prototype.sort`, no per-cell sort); the same-cell order of an alien, a meteor, an effect, a tank and so on is whatever this yields, so e.g. a cell holding a tank, a ground enemy, an effect, the alien and the meteor draws tank, meteor, effect, ground, alien. Pure, tested in `test/draw-list.mjs` (hand-simulated tie cases, all permutations of up to six distinct keys, a randomized comparison with a reference transliteration of the loop). VERIFIED by static reading of the code only; no emulator comparison of a drawn frame exists.

**Picking.** `$3F1E` scans this same sorted list, so `pickables()` returns EVERY admitted entry in sorted order, with the entry's screen box position: own tanks, ships and missiles, enemy ground and air, effects, the alien and the meteor. A hit on anything the classifier `$3F5E` does not recognise (an enemy, a missile, an effect, a special) ends the search with no target, i.e. those entries are blockers; only an own tank or ship is an order target. The direct-cell lookup (a ship, then a tank, standing exactly on the clicked cell) keeps its precedence over the list scan, and the pointer fallback is unchanged (orders.md note in `ship-control.md`). The list is not filtered by the redraw gate or by the blit's x clip.

### 7.3 Sprite descriptors and the sprite blit (VERIFIED)

- Descriptor table `$12D6A`: 21 entries of $22 bytes in the game image, followed directly by 6 more entries that are the first 6 descriptors of the scenario block (`$13034`); type t uses entry t - 1 (27 types).
- Entry layout: +0 long image address, +4 long mask address, +8 word frame size in bytes (480 or 600), +$A word rows-1 (19 or 24), +$C word unused, +$E..+$1E nine words = byte offset of each frame (indexed by byte +5 of the object, 0..8), +$20 word = bytes per plane. The address longs of the 21 built-in entries are relocated at `$7CF0` by the base `$16136` (the Disk.1 block of sectors $25C-$280, 47,280 bytes after unpacking).
- Frame layout (32 pixels wide, 20 or 25 rows): 5 bit-planes of `rows * 4` bytes, then the mask plane (mask address = image address + 5 * rows * 4), **bottom row first**, exactly like tiles. Types 1-8 are small numbered pin markers, 9-17 are vehicle-like sprites with 8-9 facing frames, 18-21 are effect animations with 3-4 frames (rendering them confirms the layout).
- Blit `$3260` (called from `$3768`): d0 = x, d1 = y of the **bottom row**, rows are written upward (stride -40), any x pixel alignment via shifts, `dst = (dst & ~mask) | (src & mask)` per plane. Objects with x < 0 or x > 255 are not drawn (`$3768..$3770`). The right clip is applied per source pixel (VERIFIED by static trace of `$3768..$3770`, `$3260`, the mask table `$4C9A` and `$32B6..$32F6`; no emulator pixel comparison). With x the sprite's left edge and p the source pixel index 0..31 (destination x + p):
  - x <= 223: every source pixel may draw (the last lands on x + 31 <= 254).
  - x = 224..254: only p with 0 <= p <= 254 - x may draw, i.e. destination columns up to 254 and never 255 or beyond (x = 224: 31 columns, 254: 1 column). Within the eligible columns the sprite's own mask still decides.
  - x = 255: **original quirk, preserved**: source index 31 aliases the scratch longword `$4D16`, which is reset to `$FFFFFFFF`, so all p = 0..31 may draw, up to destination x = 286. This is neither a clip at 255 nor at 256 and must not be "fixed".
  - The rule is one shared function (`spriteVisibleColumns` in `src/game/objects.ts`) used by `ObjectLayer.blit` and therefore by every sprite type (own units, enemies, effects, pins, alien apparition, meteor). Synthetic checks live in `test/alien-sprite.mjs` (opaque and masked sprites at x = 223, 224, 225, 232, 240, 248, 254, 255, 256) and `test/meteor-sprite.mjs`.
- For type $18 the frame address is advanced by `+8(descriptor) * 8 * byte $14(entry)` (animation counter); purpose not explored.
- Scenario descriptors (types 22-27): the scenario loader (`$8B02`, `$7D0E`) reads the record's +$10 sector pair raw to `$16136 + $BA00`, and `$8B5C-$8B80` adds that base to the six descriptors at `$13034`. Implemented in `src/data/sprites.ts`. Details, the per-type content and the unit/effect/pin logic: `units.md`.

### 7.4 Draw order interleaving, `$6540` (VERIFIED by static trace)

The 64 cells are walked in painter order and ONE cursor goes through the globally sorted list of 7.2b. After the tile of the cell with sequence `seq` (unless it was already drawn early, see below) the cursor yields every entry whose order key equals `63 - seq`:

- **Redraw gate.** If the entry under the cursor has flag bit 1 and bit 3 of `$156A9` is clear, the entry is NOT consumed and nothing is skipped or pre-filtered: the cursor stays on it, its key never matches a later cell, so EVERY later entry of the list stays undrawn for the rest of the frame (including ungated ones, and including later entries of the same cell), while tiles and the marker pins continue. The gate is reset at the outer pass and set by: an admitted own tank, an admitted own ship or missile, any visible window cell with the animated flag (bit 10), whether or not `$6936` changes its id or the power state allows the animation, and invention bit 17 (`$14472`). Enemy ground and air units, effects and the alien / meteor never set it, so an enemy in an otherwise empty, un-animated window is not drawn (an effect drawn after it is blocked behind it as well). The remake snapshots the gate once per normal `MapScene` cycle through `ObjectLayer.preparePassGate()` after the `$333A` object/special updates and `$6936` animated-cell scan, before map drawing; the bit is then retained through date/periodic work and input until the next cycle. Every video redraw uses that snapshot; a modal menu iteration keeps the previous value. Before the first loop pass, a draw computes the gate from live state. This follows the statically traced reset and source timing; exact frame-level display has no original screenshot comparison.
- **Neighbour redraw (flag bit 0: own tanks and enemy ground units).** Immediately before the individual entry is blitted, if its pixel offset (+3/+4) is not both zero and facing byte +5 is 1..5, the **neighbour cells in front of it are drawn first** so the entry appears on top of them: facing 1: (+1,-1) then (+1,0); 2: (+1,0); 3: (+1,0), (0,+1), (+1,+1); 4 or 5: (0,+1); anything else none. A neighbour is drawn only if it is inside the 8 x 8 window and its image has at most 16 rows (flat tiles; rows-1 < $10), already marked neighbours are skipped, and each drawn one is marked (bit 15 of the screen-offset word of the `$7828` entry) so that only that tile is skipped when its own turn comes (`bclr` at the start of the cell loop); the mark never hides objects. Ships, aircraft, effects and the specials never redraw neighbours. The marks and the cursor belong to one redraw (`FramePass`), not to the layer.
- then the sprite is blitted with `$3768`.

For a remake the equivalent is `ObjectLayer.drawMap`: tiles in painter order, the sorted list through one cursor (`beginFrame` / `FramePass`), neighbour redraws, the pins last. The selected view cell is passed from the current pointer hit test, and tile descriptor 58 substitutes on alternating redraws. The original tests the neighbour-redraw mark before comparing the selected cell, so a cell already drawn as a neighbour is skipped without advancing the blink bit; the remake follows that order. `test/map-loop.mjs` now checks the claimed-cell and unclaimed-cell phase outcomes using a moving own tank. Other map rendering remains a read of the game state; the selection phase is presentation state and intentionally does not mutate the saved map words. No original screenshot comparison exists.

### 7.5 Marker pins (VERIFIED)

`$14540`: 8 entries of 10 bytes {type 1..8, x, y, ...}, set by keys 1-8 at the selected cell (`$3202`), cleared by `$31CC` (`st` on the y byte). `$3310` draws them **after** all tiles and objects (not depth sorted) with the same position formula and sprite types 1-8.

## 8. Selection, picking (VERIFIED)

`$5CDA` (called on a left press from `$158CA`, and by `$3EDC`/`$2FE8`): tests the pointer against 72 rectangles at `$5E58` (16 bytes each, index `vy*9 + vx`, vx 0..8, vy 0..7): `{x0, y0, x1, y1}` = `{112+16(vx-vy), 24+8(vx+vy), x0+31, y0+14}` inclusive, then the cell word `vx<<8|vy` at +8. First matching rectangle in index order wins (rectangles overlap, so picking is rectangle-first-match, not exact diamond); a hit with vx = 8 means "no cell". Result is stored in `$14636` (-1 when none). The map cell for logic is `(scrollX + vx, scrollY + vy)` (`$6A5A`).
The original pointer is processed in `$2FBA`: if `$156A8` bit 2 (screen/pointer active) is clear it returns without drawing; otherwise it initially selects the hover descriptor at `$4AA4`. `$156A8` bit 4 (dialog busy) branches to the arrow descriptor `$4A74`; with bit 4 clear, it calls the same `$5CDA` first-match cell hit-test and also branches to the arrow when the result is negative. `$2CDA` initializes the coordinate maxima from `$15620`, overrides them to x `$138` / y `$C0` only when `$14591` is 1 or 3, then clamps the coordinates to zero..the selected maxima. The local image's `$15620` words are `$0138/$00C0`, so the remake's `mapPointerPoint` clamps select/demolish/build modes (1/3/2) to 312×192; hit testing and the rendered pointer use the same point, and the open build menu is mode 2. Both descriptors are read from the user's Disk.1 and visibility follows `Game.pointerVisible`; hover is selected only for a current hit in the active map with the build menu closed. The other Game stages use the arrow. This is a static-trace implementation with synthetic and local-data checks, not an emulator comparison. Pointer hotspot alignment follows the existing top-left convention; original-vs-browser cursor pixel alignment has not been compared.

### Per-frame background restore, `$16012` and the mask generator `$15F9A` (static trace VERIFIED against the local Disk.1 image; emulator visual parity NOT checked)
Runtime image addresses map to Disk.1 file offsets at `+$28800` (image start `$1000`). `$16012` is called once per main-loop iteration (`$157D0`, after `$333A`, before `$6936`/`$6540`) and rewrites parts of the **back buffer** (plane list `$16116`: `$6C000 + 8000*n`) so objects and tall images of the previous frame leave no trail. All five planes are processed identically, so in the remake's indexed buffer a "plane AND" is a colour-index AND (mask bit 0 gives colour 0). Four regions, in code order (nothing else is written; in particular **row 88 of x 0..255** is never touched, and neither is anything below row 159, x 272..319 or x 256..319 of rows 0..23):

| # | Region (pixels) | Source |
|---|---|---|
| 1 | rows 0..23, x 0..255 | 32x16 texture at `$16BB2`, tiled 8x horizontally; vertical halves swapped: for texture row s = 0..7, destination s and s+16 take texture row s+8, destination s+8 takes row s (`$16012`-`$16046`; per plane the texture is 16 longs = 64 bytes, one long per row) |
| 2 | rows 24..87, x 0..255 | the same texture, **row r in layer rows 24+16L+r**, tiled 8x, ANDed with a long of the pattern table (`$14640`): layer L (0..3) reads `$14640 + $200*L`, row r reads the 8 longs at +32*r, so vector index e = 16L + r selects the entry; bit 31 of each long is its leftmost pixel (`$16048`-`$1609A`) |
| 3 | rows 89..159, x 0..255 | saved bitmap at `$26372`: 71 rows x 32 bytes per plane, 5 planes, 11,360 bytes (`$1609E`-`$160CA`) |
| 4 | x 256..271, rows 47..96 | saved bitmap at `$2617E`: one word per row, 50 rows per plane, 500 bytes, ending exactly at `$26372` (`$160CC`-`$160F0`) |

**Where the sources come from (VERIFIED, static):** `$4E28` first swaps screen buffers, then `$7D24` unpacks the picture into screen A `$75E00`. It calls `$2B1A`, which copies 40,000 bytes from A to B and loads the palette from `$7FA40`; it does not unpack the picture itself. After `$309E` only switches the software pointer off, `$4E28` copies from screen A without drawing in between: the texture at `$4E7E`-`$4EC0` (long at byte `$10`, i.e. x 128..159, rows 0..15, from each plane at 40-byte stride, into `$16BB2`), the `$26372` snapshot at `$5028`-`$5052` (row 89, byte 0, `$de8` = 89*40) and the `$2617E` snapshot at `$5056`-`$5076` (row 47, byte 32, `$778` = 47*40 + 32). They are only read by `$16012`; a scan for absolute-long references found no other code reference to `$16BB2`, `$26372` or `$2617E` (register-relative accesses were not excluded). So regions 3 and 4 reproduce the freshly unpacked picture, and region 1 and 2's texture is the picture's own strip; the restore is a pure function of the picture (no game state). The same picture setup path also runs at `$15702`, before `$15F9A`.

**Back-buffer cadence (VERIFIED, static):** the game loop calls `$16012` at `$157D0`, then `$6936`, `$6540` and `$3310` draw into the plane list at `$16116`. After date work, the VBL-flag wait at `$15846`, and `$99C4`, `$15838` calls `$4E08`; that routine swaps the two 7-long screen blocks at `$160F2/$1610E` and loads the new copper-list pointer into `$DFF080`. `$16116` is the second block's five-plane pointer list, so after the swap the next main-loop iteration restores and draws into the other bitmap. Each bitmap therefore retains its own untouched pixels from its previous use (two main-loop iterations earlier); the per-iteration `$16012` clears only its four traced regions. This ordering follows the static caller and swap routines, not an emulator pixel capture.

**The mask pattern, `$15F9A` (called once at init, `$15714`, after `$15F84`):** it fills the `$14640` table (0x800 bytes = 64 vectors of 8 big-endian longs d0..d7) with a state machine: `a0 = $14640 + $7E0` (vector 63) gets all zeros first. Then d0 = `$C0000000`, d7 = 3, others 0 and 63 times (loop counter held in a2 via `exg`): store d0..d7 at the downward pointer (vector 62, 61, ... 0) **and** at an upward pointer starting at `$14E40`, then two passes of `ASR.L #1,D0; ROXR.L #1,D1; ROXR.L #1,D2; ROXR.L #1,D3; ASL.L #1,D7; BSET #0,D7; ROXL.L #1,D6; ROXL.L #1,D5; ROXL.L #1,D4`. d0..d3 act as one 128-bit arithmetic right shift (the ASR keeps the sign, so each pass adds a 1 at the top; bits leaving d3 are lost because the `ASL` resets X), d4..d7 as a 128-bit left shift with a 1 inserted at bit 0 (the `ASL`'s carry feeds d6). Closed form: vector e (0..62) has 126 - 2e one-bits at the top of d0..d3 and 126 - 2e at the bottom of d4..d7, vector 63 is zero. Visible pixels of row 24+e (x 0..255): x < 126 - 2e and x >= 130 + 2e, so row 24 hides only x 126..129, row 40 x 94..161, row 86 shows x 0,1 and 254,255 only and row 87 shows nothing (colour 0). The upward stores write the same 63 states in generation order to `$14E40`..`$1561F` (0x7E0 bytes); **no consumer of that region was identified** and its purpose is unknown (the range is zero in the Disk.1 file and ends just below the `$15620` pointer-limit words; absolute-long constants elsewhere in the code point into `$14E40`..`$1561F`, so it may hold variables that later initialisation overwrites; this was not traced, and the remake models no state there). The remake's generator reproduces both streams (`generateMapPattern().tail`) but nothing reads the tail.

**Remake:** `src/game/map-background.ts` (`generateMapPattern`, `restoreMapBackground(initial, current = initial)`). `MapScene` keeps two persistent indexed pixel buffers. On each scheduled normal main-loop pass it selects the alternate buffer, applies `$16012` to that buffer (restoring the four traced regions while retaining its other pixels), draws the map and overlays, and keeps that completed image until the next use. Video updates between passes do not redraw or swap; modal menu updates redraw controls over the current image without swapping. Scene creation paints an initial frame without advancing the loop. This follows the statically traced double-buffer cadence; the browser's configured pass interval and input/frame timing remain approximations. No emulator frame comparison establishes pixel parity or whether preserved untouched-region history produces visible differences. On the player's local picture the restore changes only pixels inside x 0..255, rows 0..87 (7,034 of 22,528 pixels in this checkout), the rest equals the decoded picture. `test/map-background.mjs`: asset-free checks (closed-form and hand-derived vectors, SHA-256 of the table and tail from an independent Python model of the 68k shifts, per-pixel placement of all 64,000 pixels against a hand-written predicate, untouched pixels, no input mutation) plus one local-picture region check. A live `MapScene` integration check confirms the generated background reaches the screen buffer.

**Overlay areas (remake-side, bug fix 2026-11-07):** the remake redraws command-button flips (an XOR, `$57D6`), the mode frame, the side preview (272, bottom row 52), the message line and the log from state every pass, but `$16012` never restores x 272..319 or rows 160..199, so with persistent bitmaps stale pixels stayed and an XOR flip blinked every second pass (and expired messages never vanished). The original keeps these correct by events instead (flip on press / back on release in both bitmaps `$5756`/`$57FA`; message and log erase from pristine strips in both bitmaps `$558A`/`$5C9A`, game-text.md 4-5). `MapScene.restoreOverlayAreas()` therefore resets rows 160..199 (full width) and x 272..319 rows 22..159 from the pristine picture before the overlays are drawn: same visible result, not the same mechanism. Unchanged and still history-dependent: row 88, the top bar right of x 255, x 256..271 outside rows 47..96. This is derived from static code and a source reading, no frame comparison and no test run.

Unresolved (HYPOTHESIS/unknown): the role of `$156A8` bit 5, which gates the `$5A16` copies and the button redraw in `$B628`/`$B680`; whether the first browser-presented map frame after a fresh scenario transition matches the original pixel-for-pixel (the remake now runs its immediate first pass before presenting that frame, but no emulator frame comparison exists); and the exact frame on which the original shows the pre-menu frame after exit.
