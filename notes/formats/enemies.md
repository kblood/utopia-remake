# Enemies, combat, ships and guns (static analysis of the game image; port in `src/game/enemies.ts`)

Status tags: [V] read from the disassembly, [H] hypothesis / guess. Addresses are image addresses (file offset = address + $28800).
No game data is stored in the port: the lookup tables are read from Disk.1 at runtime by `src/data/combat.ts`.

## 1. Main-loop pass `$333A` [V]

Sub-tick `$144C9` counts 0..8. Wrapping to 0 sets the **move tick** (`$156A9` bit 7), reaching 4 sets the **enemy tick** (bit 6); both last
one pass. Per pass: own tanks (units.md), ships (`$42BE`, then own fire if `$145A4[class]` != 0, not for type $11), enemy ground (`$1193E`),
enemy air (`$11A9E`), effects, alien animation / meteor / wave-spawn work, draw sorting, day advance and `$99C4` after the VBL wait. Bit 7 of record byte +9 = "waiting for the next move tick": own tanks start waiting, are cleared by the first
move tick and then step every pass; the fire routine `$12588` (move tick only) sets the shooter waiting again. Enemy ground units are stepped on the
enemy tick or whenever they are not waiting (an attack sets them waiting). Aircraft have no waiting check. `PassClock` (units.ts) holds the flags;
`ObjectLayer.update()` runs `units.tick()` then `enemies.pass(clock)` once per main-loop pass (`MainLoop`, 4 video updates by default, the pass length observed on Copperline only: `map-rendering.md` section 6 "Main-loop timing"). While paused it only advances the clock. `Sim.pass()` then advances alien/meteor/spawn state; `Sim.periodicPass()` follows the date advance and VBL wait, running `$99C4`. Gun firing consumes original pending-period bits and is not inferred by sampling countdown at pass boundaries.

## 2. Enemy record (stride $1A; ground slot 0 at `$3A146`, air slot 0 at `$39E3A`; the pass loops `$349C` / `$3506` start from `$3A12C` / `$39E20` and add the stride before their first test) [V]

+0 type (22/23 walker, 24 crusher, 25 bomber, 26/27 kamikaze, 9/10 defected tank), +1/+2 cell, +3/+4 pixel offset, +5 direction, +6/+7 velocity,
+8 hit points, +9 mode, +A tech, +B/+C target cell ($FF = none), +D step counter, +E bomb chance %, +F damage, +$10 lift (air) / recent directions (ground),
+$13 aux (bomb count of a bomber, dive height of a kamikaze, crusher toggle), +$14, +$15, +$16 flag pointer.
Spawn init (`$48B6` air, `$48EC` ground) from the wave entry (`EnemySpawn.entry`): wave level at `$13467` is copied to +A; hp = e[1], +F = e[3], +E = e[6], +$13 = e[5], +$14 = e[6], +$15 = e[7], mode 6, target `$FF`; aircraft start with lift `$22`. The allocator checks the count word before scanning the first free slot. At creation it sets only the map occupancy bit and increments `$142A2` / `$142A4`; `+$16..+$19` and the flag byte are left untouched (the slot keeps whatever pointer it had; a never-used slot held 0 in the one snapshot we have) and the flag-byte mark and a new `+$16` arrive with the first movement claim (section 3b). A failed allocation leaves that queue entry pending and continues to the next bounded queue try; if all eight cells are blocked, the spawner exits immediately with that entry still queued. These are static Disk.1 traces, not live-original observations. Synthetic regressions of the initialized bytes, occupancy-only mark, full-list refusal and subsequent queue try run through the real `Sim.aliens.spawnStep()` -> `EnemySystem.spawn` path in `test/enemies.mjs`; the hook payload is checked in `test/aliens.mjs`. No live invasion or combat parity is claimed.
Map marks: ground unit = word bit 14 (`$4000`) + flag bit 0, aircraft = word bit 13 (`$2000`) + flag bit 1; own tank flag bit 2, flying ship flag bit 3.

## 3. Behaviour [V unless tagged]

- **Walker (22/23, `$1197C`)**: mode 6 picks a random building (`Sim.randomBuilding`) and goes to mode 1; mode 5 idles; otherwise the shared walk
  step `$38E2` (units.ts `walkerStep`, enemy variant) and, when the target is done, mode 6; then the attack. Defected tanks (types 9/10 in the enemy list) spin
  (dir - 1 each step) and attack.
- **Crusher (24, `$11F12`/`$11F42`)**: steps on every second call, counter 0..7 with an animation table (`$12D60`) feeding the sprite's second dimension; walks over
  rocks (low byte >= $88) and active buildings ($0400, destroyed with `Sim.bomb` as it claims the cell); acid tile $61 hurts it by `byte($13116) + 2 * tech`;
  mode 1 lasts at most 80 steps. It does not shoot. Arrival, the candidate order, the occupancy/destruction ordering and the saved `+$13`/`+$14` fields
  are in section 3a (earlier revisions of this note guessed that arriving clears the velocity; the trace says only `+B` changes).

### 3a. Crusher step and saved state (`$11F12`, `$11F42`, `$1228A`, `$1231A`) [static trace; not observed in the running original]

Evidence level: read from the disassembly of the Disk.1 game image by an earlier work item and encoded as the expected values in `test/disk4-crusher.mjs` (its
header lists each address). A later session re-read the notes and tests for consistency but did not re-trace the binary and has no emulator observation of a
crusher; everything below is therefore [V]-by-trace with the single-source caveat, except the lines tagged [H].

- **Record fields.** `+$13` packs two values: bit 7 is a toggle (`bchg #7`), the low 7 bits are a step counter. `+$14` is the animation (the repeat count added
  to the sprite frame address by `$3768`, so it indexes the three frame sets of the type-24 sheet); it is only ever written from table `$12D60[counter]` (`$11F6E`)
  or, at spawn, copied from the wave entry (`$496E`/`$4974`: +$13 = e[5], +$14 = e[6]). A walker/bomber/kamikaze uses the same bytes for other things; only a
  type-24 record is split this way. In the port: `Enemy.toggle` / `counter` / `anim`, `Enemy.aux` and `p14` keep the raw bytes.
- **Gate (`$1193E`).** +9 bit 7 set = waiting: nothing happens until the enemy tick clears it. `$11F12`: mode 6 sets +D = 0 and picks a building target (`$119AC`,
  mode 1); mode 1 runs `$11F42`, then +D = +D + 1 as a byte, and goes to mode 6 when +D == $50 or +B is negative; any other mode does nothing. A saved +D above $50
  therefore wraps through $FF to 0 before it can stop the walk.
- **Step (`$11F42`).** +B negative (the no-target marker `$FF`, but any `$80..$FF`) returns before `+$13` is touched. Otherwise `bchg #7,$13`: if the old bit was clear the
  call only sets it and returns (every second call does nothing); if it was set the bit is now clear and the counter becomes `counter - 1`, below 0 becomes 7,
  stored back, and `+$14 = $12D60[counter]`. Then the shared walk step runs with byte arithmetic: offset += velocity as `add.b`, compared with the `$4C1A[dir]`
  distance as `cmp.b`, both wrapping at 256.
- **At a cell centre.** Target reached: `$1231A` only does `st.b $B(a6)`: +B = $FF. +C, velocity, direction, pixel offset and the reservation all stay, so the crusher
  keeps its old velocity until a new target is picked and then slides one cell on in its old direction into a cell it never reserved. The reserved cell it arrived in
  keeps its occupancy bit and flag for good (the next step clears only the marks of the cell the unit now stands on), which the tests encode as a stale mark. Acid tile ($61) is checked before the direction is chosen, so not on the
  target cell: `hp -= byte($13116) + 2 * byte($14592)`, `bgt` survives, otherwise the unit is destroyed through `$11C5C` (release the `+$16` cell, `$142A2` - 1, kills + 1).
  Control flow as encoded in the port and test (static trace, not re-traced in the latest review pass): the acid check (`$11ECA`) runs at the cell centre
  before any candidate direction is examined, and it is the acid death that selects the explosion, then enters `$11C5C`. `$11C5C` itself does not decide it:
  a border exit (below) reaches the same `$11C5C` from the candidate scan, never through `$11ECA`, and so has no explosion
  (`EnemySystem.destroyGround(e, explosion)`: `true` from `acid()`, `false` from `leave`).
- **Candidates.** `d` is the direction from the unit's cell toward the target cell (the greedy choice made at the cell centre). The direction slots are d, d+1, d-1, d+2, d-2, d+3, d+3 (`$4BCA` row, entries +0..+5, +5 again: `$12234` repeats d+3 instead of trying d-3,
  as the advanced tank does). A direction listed in `+$10..+$12` is skipped; if it is the last slot the order ends. A candidate off the map (border word `$73FF`)
  destroys the crusher through `$11C5C` without an explosion and without an acid check. Enterable = not blocked, or blocked with the low byte N-clear after `cmpi.b #$88` (rock; this also admits
  $00..$07 by wrap-around), or blocked with bit 10 (an active building). If the last slot is enterable but occupied the 8 bytes saved by `$4B6E` (+0..+7: x, y,
  offset, direction, velocity) are restored and the target is kept (retry next call); the toggle/counter update is not undone. If the last slot is blocked, `$1231A`.
- **Claiming order (`$1228A`/`$122B4`).** The next cell's occupancy bit (bit 14) is set, then a building there (bit 10) is destroyed (`$7124`/`$12332`, `Sim.bomb`),
  and only then `$122B4` clears the old cell's bit 14 / flag bit 0, sets the next cell's flag byte, stores the new `+$16`, and writes `+$10..+$12` (the reverse
  direction and its two neighbours), +5 and the velocity. The port exposes that point as `StepEnv.claimed` and the arrival/candidate quirks as `StepEnv.arrive`,
  `repeatLastCandidate`, `byteOffsets` of the shared `walkerStep` (`src/game/units.ts`).
- **[H] Sliding off the map.** A crusher that keeps its velocity after arrival can end a step in a cell outside the map. The original would read pad words there
  (untraced); the port treats it as leaving the map (border path: the unit is destroyed without explosion, the reservation released). Tagged untraced in the test.

Restore policy (`EnemySystem.fromRoster`, `Enemy.fromDisk4`): a saved type-24 record is adopted with `toggle` = bit 7 of `+$13`, `counter` = its low 7 bits and
`anim` = `+$14`; no field is defaulted or invented. Adoption is refused (typed `unsupported-state`, reason `crusher-counter` / `crusher-anim`, all-or-error, before
anything is installed, the roster stays adoptable) only when the counter is above 7 (`$11F68` would index past the 8-byte table) or `+$14` exceeds the largest value in
`$12D60` (no such frame set exists). The exact byte values of `$12D60` are not recorded in this repository; the tests use a synthetic table and the optional local-data block checks only its bounds (8 entries, minimum 0, maximum 2). The first bad slot is reported, the counter before the animation. All other saved crusher states (any toggle value, any +D,
mode, offset, velocity, recent directions) are continued by the traced step above. Whether the original's own save routine can produce a counter above 7 is not
known; the refusal is a conservative domain check, not a claim about the original. Disk.4 crusher continuation is covered only by synthetic tests; it has not been compared
with the running original.
- **Aircraft step `$11AE6`**: type 27 moves at double speed; the air-layer mark moves to the next cell when a step starts; leaving the map destroys the unit with
  morale +50 (`$11C30`).
- **Bomber (25, `$11C7A`)**: mode 6: steps = 0, pick a target; mode 1: fly, after 20 cell moves back to mode 6, about 10 % chance per cell move to try a bomb run.
  A bomb run only works over an active cell: +$13 --; below 0: mode 6, and if +$15 == 0 then +$13 = 0 and mode 3 (flies straight off the map); otherwise bomb the
  cell when `roll(100) < +$14`. With +$13 < 0 the unit behaves as a kamikaze.
- **Kamikaze (26/27, `$119C0`)**: mode 6 picks a target and sets +$13 = stored height - 10 (section 3c); mode 1 flies; on arrival at an active
  cell: mode 2, dir 3, velocity 0 (else mode 6); mode 2 lowers the lift by 2 (4 for type 27) and detonates when +$13 >= lift: `destroyAir` then `Sim.bomb`. Type 26
  and bombers also call the attack routine.
- **Attack (`$1266A`, enemy tick only)**: scan the 48 cells of the spiral table `$12C96` (stops at the map edge). The original reads CIA TOD low byte `$BFE801` once per attack call; the gate opens iff its unsigned byte is 0..24. All active-building cells in that scan share that one gate value. When open, an active cell is bombed with chance +E %. Flag bits 2/3 (tank / ship): the tank within +-1 is hit for +F (destroyed -> `$4692`), otherwise a ship (`$46CC`). The attacker waits afterwards. The remake injects a separate deterministic hardware approximation (`SimOptions.hardware`); it does not consume Sim RNG or reproduce wall-clock TOD.
- **Own fire (`$12588`, move tick only)**: the first cell in the spiral with flag bit 0 or 1 selects the enemy within +-1 (none: scan ends); hit sound, shooter waits,
  hp -= `$145A3` (tank) or `$145A4[class]` (ship); at hp <= 0 the enemy dies with an explosion (air: morale +50).

### 3b. The per-slot `+$16` pointer: spawn, claim, death, reuse [static Disk.1 trace; one zero-pointer observation; not a live-original run]

Evidence levels, kept apart:

- **Static trace (Disk.1 disassembly, read by hand; not observed in the running original).** The wave allocators `$48B6` (air) and `$48EC` (ground) write the type, hit points, `+A`, `+E`, `+F`, `+$13`, `+$14`, `+$15`, mode and target bytes, and leave
  `+$16..+$19` (the flag-pointer long) and the per-cell flag bytes untouched; the only map write of a wave spawn is the occupancy bit in the map word. The first movement claim of the enemy (`$3BC6`-style for walkers, `$122B4` for crushers, the aircraft step for
  air) stores a new `+$16` (`$3D3A6 + y * $66 + x` of the claimed cell) and sets the flag bit there. The destroy routine `$4732` loads `a4` = the **stored** `+$16` and `a6` = the matching map-word pointer
  (`$3F256 + 2 * (a4 - $3D3A6)`; the map rows are 102 words in memory, 100 cells + 2 pad words), it never looks at x/y; it clears only the record's `+0..+2` and `+8/+9` (units.md 5), so the `+$16` long **stays in the fixed slot** after death and is still
  there when `$48B6` / `$48EC` hand the slot to the next wave enemy. That enemy dies, if it dies before its first claim, through the OLD pointer.
- **One observation (not a proof of initialisation).** One external pre-November RAM snapshot (taken before any enemy spawned, one scenario, one machine) held all 90 free enemy `+$16` longs (60 ground + 30 air) at 0. That is the only evidence for the
  value of a never-used slot. **Initial RAM at first boot is not established as universally zero**: a different boot path or an earlier session in the same RAM could leave other values. The remake starts every never-used slot at 0; adopted Disk.4
  rosters and native saves bring their own values.

Port (`EnemySystem.groundFlagPointers[60]` / `airFlagPointers[30]`, `src/game/enemies.ts`):

- **The raw pointer is separate state.** Every fixed slot, free or occupied, owns one unsigned 32-bit long. It is not derived from x/y and is not cleared by death or spawn. `Enemy.reserveX/Y` is only a **mirror**: the playable cell the slot's pointer
  currently names, or `-1 / -1` when it names no playable cell (zero, padding column 100/101, outside the array). The pointer is the authority; saves and Disk.4 rosters store the pointer.
- **Wave spawn** (`origin: "wave"`, from `$1187C`) leaves the slot pointer and the flag byte alone and sets only the map occupancy bit (`$4000` ground, `$2000` air). A fresh never-used slot therefore has pointer 0 and mirror `-1 / -1`; a reused slot
  keeps its stale pointer and the new enemy's mirror shows the stale cell. A spawn without `origin` (the staging path of tests and direct fixtures) keeps the historical behaviour: map bit, flag byte and pointer = the spawn cell.
- **First movement claim** (ground via `StepEnv.entered` -> `claimGround`, air via `airMove`) stores `cellFlagPointer(claimed cell)` in the slot (an aircraft stepping to a cell off the map still stores the raw 32-bit pointer; only a playable cell gets
  the map / flag marks) and updates the mirror. Event tank defection (`defect()`) writes the pointer of the cell it marks (the tank's current cell).
- **Death** (`destroyGround` / `destroyAir`) resolves the slot's **stored** pointer with the true 102-byte row layout and releases what it names: the flag bit (ground bit 0 / air bit 1) and, unless the kill's `$1237C` clobbered A6 (section 6), the map
  occupancy bit (`$4000` / `$2000`). Consequences, all from the static reading:
  - death **before the first claim** of a fresh slot (pointer 0): nothing is released; the spawn cell's map bit stays set (it leaks, as the old HYPOTHESIS "release the spawn cell" is superseded) while counts and kills are updated;
  - death after the first claim releases the claimed cell;
  - death of an enemy in a **reused slot before it has moved** releases the **stale** cell of the previous occupant (flag bit and map bit, even if another unit stands there now) and leaves its own spawn cell's map bit set;
  - a pointer that names a padding byte (column 100/101) or lies outside the flag array releases **nothing** in the port (only a playable cell is released; the remake's packed map array has no pad words, and the original's effect on a padding byte
    is not modelled). This is a deliberate bounded simplification, not observed behaviour; the remake never **sets** a flag byte on a non-playable cell.
- The freed slot keeps its raw pointer, so the next wave spawn into it starts with that stale value (first bullet above).
- **Limits.** Static reading plus synthetic tests (`test/enemies.mjs`, `test/disk4-enemies.mjs`, `test/save.mjs`). No live capture of a pre-claim death, a slot reuse, or a padding / out-of-range pointer exists, and the first-boot value of a never-used
  slot rests on the single snapshot above. No original combat parity is claimed.

### 3e. Freed-record bytes: what a death changes, what a new occupant inherits, who reads a free record [static Disk.1 trace, 2026-11-10; no emulator comparison]

Question answered: does a freed enemy slot need its raw record bytes kept (for spawn reuse, save, checkpoint or Disk.4)? **No.** Every reader of a free record tests its type byte first except the cases listed below, the readers of x/y see the zeroed values that `$4732` stores, and the next spawn rewrites every other byte that is ever read. Pinned by `test/freed-records.mjs` section 4 (static byte pins from Disk.1 plus behaviour). File offset = address + `$28800`.

**What a death writes** (`$11C5C` ground, `$11C30` air, both calling `$4732`):

| Step | Ground (`$11C5C`) | Air (`$11C30`) |
|---|---|---|
| counter | `$142A2`-- (word, no clamp) | `$142A4`-- (word, no clamp) |
| kills | `$14298`++ (long) | `$14298`++ (long) |
| blast lift | none: `$12D68` stays 0 | `$12D68` := +$10 (the lift) before `$4732` |
| `$4732` record stores | +0 word, +2 byte, +8 word := 0 (type and x, y, hit points and mode) | same |
| `$4732` blast | if bit 5 of `$156A9` is set: `$1237C` at the cell read from +1/+2 **before** the clear (`$4732` loads d2/d3 first; `$1237C` takes the cell from d2/d3) | same |
| map word | `bclr #6` (`$4000`) at the cell +$16 names, unless the blast clobbered A6 | `bclr #5` (`$2000`), same rule |
| flag byte | `bclr #0` (`FLAG_GROUND`) at the cell +$16 names, always | `bclr #1` (`FLAG_AIR`), always |
| morale | none | `$A246`(+50) |

Not written by any death: +$16..+$19 (the slot's pointer, section 3b), +3..+7, +$A..+$F, +$10..+$15 and the rest of +9 (bit 7 included). `$4732` writes +0..+2 and +8/+9 only.

**Port** (`destroyGround` / `destroyAir`, `src/game/enemies.ts`): the slot is freed, the blast is taken with the pre-death x, y and lift, the named cell is released as above, counters and morale follow. Differences, none reachable with a consistent original image:
- Counters clamp at 0 (`Math.max(0, …)`); the original wraps. The wave guard is `>=` capacity where the original compares for equality (`cmpi.w #$3c` / `beq`); the two differ only above capacity. A Disk.4 import range-checks the count word (`readCount`) but does not compare it with the occupied slots, so an inconsistent saved count is the only way to reach either difference. Left as is.
- Air morale is applied before the blast and the original applies it last; the port clears the flag before the blast and the original after. `blastCell` reads only the effect pool and the sound, so neither order is observable.
- A pointer that names no playable cell (zero, padding, off the map) releases nothing in the port. The original runs the same `bclr`s at the computed address. For a zero pointer that is the byte at address 0 (flag) and the map word at 24-bit `$FC4B0A` (`$3F256 + 2 * (0 - $3D3A6)`, Kickstart ROM on an Amiga, where a write is ignored). **HYPOTHESIS:** both are no-ops, so the port's skip is equivalent; not verified. This is the one stray-write class left unmodelled, and it occurs on a death before the first claim of a never-used slot.

**Stray writes into a free record.** The only write of a missile into a freed record is the `$4408` arrival on a FREE target (type 0 takes the ground branch): `st.b $B(record)` (= $FF) and `move.b #5,$9(record)` (= 5). The missile side (mode 2, dir 3, velocity 0) is ported. These two bytes are not kept, because nothing reads them (next list) and the spawn rewrites them (after it).

**Who reads a free record** (type byte +0 is the first test, unless noted):
- Enemy passes: the ground loop (`$349C`-`$34A2`, `tst.b (a6)` then `beq`) and the air loop (`$3506`-`$350C`): a free record is skipped before +9 or any other byte is read. `$3694` (position window) is called only after that test.
- Cell scan `$49AA` (callers `$11E4C`, `$125E8`, `$1262E`, `$126EA`, `$12734`): `tst.b (a1)` skips a free record. The scan of `$3A12C` at `$12470`: the same.
- Free-slot searches: the spawn allocators `$48B6` / `$48EC` and the defection search `$11590`-`$115A8` test the type byte only.
- `$ACE2` (daily missile step): `tst.b (a0)`; a free slot destroys the missile (`dailyMissile`, ported).
- `$4408`: mode 1 compares the POINTED record's +1/+2 (zeroed by `$4732`, so cell (0,0), ported) and its type (zero: ground branch, ported); the `tst.b (a6)` at 44C2 returns silently for a free record (ported).
- Native saves and checkpoints serialise only occupied records. The native save keeps the raw +$16 pointer of every slot (section 3b); nothing else of a free slot is stored.

**What a spawn overwrites** (`$48EC` / `$48B6`, both branches reach the shared tail `$4924`-`$497A`): +0..+5 (type, x, y, +3 = +4 = 0, +5 = direction), +6/+7 (zero), +8 (hit points), +9 (= 6), +A (tech), +B and +C (= $FF), +D (= 0), +E, +F, +$13, +$14/+$15. The ground branch also stores +$10 and +$11 (word $FFFF) and +$12 = $FF; the air branch stores +$10 = $22 and nothing else of +$10..+$12 (so an air record keeps the stale +$11/+$12 of its previous occupant). Not written by a spawn: +$16..+$19 (section 3b).

**Air +$11 / +$12 are never read.** Air code reads only +$10, as lift (`$11A2A`, `$11A34`, `$11A3C`, `$11C3C`; the missile reads its own +$10 in `$4408`). The recent-direction triple +$10..+$12 is read by ground code only: the crusher step `$11F42` and its direction test at `$11FE0`-`$12248` (called only from the crusher dispatch `$11F26`), and the walker step `$38E2` (direction test at `$39EC`-`$39F8`). So the stale air bytes are unobservable.

**Conclusion.** No free-record byte other than +0..+2 is read before the next spawn rewrites every byte that is read later. The air +$11/+$12 are stale but never read, and the pointer is kept per slot (section 3b). Keeping raw freed-record bytes would store values that no routine reads, so it is not implemented and the save version stays 9. The remake's model (a freed slot is `null`; a spawn builds a fresh `Enemy`; the per-slot pointer is kept) gives the same result for every reader above.

**Event-17 defection (`$11566`), the one other writer of a free enemy slot** [static Disk.1 trace, 2026-11-10; no emulator comparison; port: `EnemySystem.defect()` and `UnitSystem.vacate()`]. Sequence: the first used own-tank record (`$3AB1E`, stride `$18`) is taken; the free-slot search `$11590`-`$115A8` takes the first free ground slot (scan from `$3A146`, 60 records); `$142A2` is incremented and `$1429C` decremented. **Copy:** `$115BA`-`$115BE` move the tank's 16 bytes +0..+F into the slot (`movem.l`, four longs). `$115C2` clears the slot's +6/+7 (velocity), `$115C6` writes +$E = 10 and `$115CC` writes +$F = `$145A3`. `$115D4` clears only the TANK's type byte (`clr.b (a0)`). **Kept from the tank:** type +0 (9 or 10), cell +1/+2, pixel offset +3/+4 (drawn by `$3694`), facing +5, hit points +8, control +9 (bit 7 = waiting; the low bits are the mode, `$7F` for a tank that has moved), tech +A, target +B/+C. +D is 0 for a tank (units.md 3; the Unit record does not store it). **Not copied:** +$10..+$15 keep the slot's previous bytes; no reader of them was found for types 9/10. **Flag and map:** `$11432` sets the focus bookmark (`$144E8`, `$15644`, `$144BD`); `$497E` gives the flag byte of the tank's (x, y); `bclr #2` (own-unit flag) and `bset #0` (ground flag) act on that byte, and +$16 = that pointer (`$115FE`). No map word is written, and the tank's reservation is NOT released: a unit's reservation is the NEXT cell while it moves (units.md 5), so a tank defected between cells leaves bit 14 and its own-unit flag on that reserved cell. The message `$181` is posted once. **First readers of the converted record:** the enemy ground pass `$349C`-`$34C6` (off the enemy tick a waiting record is skipped without any change; on the enemy tick bit 7 is cleared and the record is stepped, so a waiting defector first acts on the next enemy tick, a non-waiting one on the next pass); the dispatcher `$1193E` (types 9/10 ignore the mode bits); the spin `$1196E` (+5 minus one, 0 wraps to 7); the shared attack `$1266A` (enemy-tick gated; reads +1/+2 and `$497E`; sets bit 7 of the attacker's +9 when it hits a target in the `$126DC` branch, `$12706`, so the defector waits again); the draw window `$3694` (+1/+2, +3/+4 offset, +5 only at the window edge). **Port** (`defect()`): the same copy and flag writes; it keeps the tank's waiting bit, offset, tech and targets, and mode `control & $7F`. The former divergences (mode 5, zero offset, waiting false, a released reservation, a written map bit) are gone. ### 3d. Target pick miss (`$119AC` / `$11A5C`): stored fields, callers, downstream [static trace; no live miss observed]

Evidence: Disk.1 disassembly (`tools/game_dis.py`, file offset = address + `$28800`). Nothing here has been seen in the running original; the scenario that could reach a miss (no used building record, or a count word above the used records) is not in any capture.

- **`$119AC`**: `bsr $11A5C`, then `move.b d2,$B(a6)`, `move.b d3,$C(a6)`, `move.b #1,$9(a6)`, `rts`. The three stores are unconditional: they run on a hit and on a miss.
- **`$11A5C`**: one `$2DCC` draw with range `min($142C2, $FE)` (signed compare), then a scan of the 1000 object records (`$3B466..$3D3A6`, stride 8) for the skip-th record whose first word is non-zero. - **Stored on a miss**: +B = `$FF` (the remake's `NO_TARGET`, bit 7 set, so the walk and crusher gates read it as "no order"); +C = the **low byte of D3 at entry**; +9 = 1.

**D3 at entry is register residue, not a caller value.** None of the four callers sets D3: walker `beq $119AC` at `$11980` (from `$1197C`), crusher `bra $119AC` at `$11F1C` (from `$11F12`), bomber `bra $119AC` at `$11C8C` (from `$11C7A`), kamikaze `bsr $119AC` at `$119C6` (from `$119C0`). Which of these survives into the next enemy depends on the previous enemy and on `$497E`, whose register use is untraced. **Status: not established.** The port has no register model and keeps +C = `NO_TARGET`.

**Downstream on a miss, per type**

- **Walker (22/23).** On the next pass `$1197C` (mode 1) calls the walk step `$38E2`, which does `bmi $3C3C` on `+B` before it reads `+C`, the direction or D3 (`$3C3C` is `movea.l (a7)+,a4; rts`). Disk.4 hydration: `EnemyRoster.fromDisk4()` / `Enemy.fromDisk4()` fill fixed 60 ground / 30 air slots from decoded saved records (see game-proper.md section 6, Disk.4 notes). For ground records, `+9` is split into `mode` (low 7 bits) and `waiting` (bit 7), with the full byte kept in `savedControl`; for air records, +9 stays an uninterpreted full mode byte because aircraft have no wait gate (their attack step clears bit 7 after `$1266A`, section 3d). The reservation comes from the `+$16` pointer (102-byte rows), and the raw record stays in `sourceRaw`. `EnemyRoster.groundPointers[60]` / `airPointers[30]` hold the raw `+$16` unsigned long of **every** decoded slot, free ones included (a free slot's stale pointer is copied exactly, never inferred from x/y or cleared); `EnemySystem.fromRoster` adopts those arrays as the system's `groundFlagPointers` / `airFlagPointers`. **Any unsigned long is accepted on occupied and free records alike** (zero, padding column, outside the flag array, a stale cell): an allocated wave enemy is occupied before its first claim and the allocators leave the tail untouched, so a non-playable pointer is a legitimate occupied state, and the one captured pre-run only supports zero for that scenario. The raw long is kept; `reserveX/Y` is the named cell only when it is playable, else `-1 / -1`; death releases only a playable cell (section 3b). A value that is not an unsigned 32-bit integer is still a typed `flag-pointer` refusal. That keeps the pre-claim death of a reused slot faithful to section 3b after a Disk.4 adoption. `prepareDisk4HeadlessEnemies()` builds on `prepareDisk4ShipLoad()` and adopts both rosters into one `EnemySystem` via `EnemySystem.fromRoster(sim, units, tables, enemies, hooks, ships)`. Adoption retains the exact objects and fixed slot arrays (enemy 60/30 and the 40 ship slots, holes included); it does not spawn, step, count, or write map/flag/state/object buffers, and it calls no RNG or hooks. Validation is complete before any slot is installed, so a failure returns no partial controller. Enemy movement advances explicitly through `pass(clock)`; gun periods run through `Sim.periodicPass()` (inside the headless `Sim.loopPass()`), while `frame()` is a legacy no-op. Ground/air runtime lists allocate in the first free slot: original scans `$48EC` (ground, 60 slots) and `$48B6` (air, 30 slots) verify this order. Destroying an enemy clears its own slot and leaves survivors in place. Restored missiles (type 17, `RestoredMissile` = the shared `MissileRecord` plus provenance, no class/fuel) keep `target.ref {list, index, address}` as the authority and the system resolves the CURRENT occupant of that enemy slot at run time, so a dead enemy is never kept across slot reuse; launched missiles use the same `ShipExtra.targetSlot` identity and the same step, and the main-pass flight (`$4408`) and the daily `$ACE2` refresh/destroy follow the traces in ship-control.md 5c/5d. Saved ships get `ShipExtra` (`vx/vy`, `next`, `turn`, reservation `rx/ry` from `+$14`) from their saved bytes instead of defaults.
