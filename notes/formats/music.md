# Music: modules on Disk.1 and the player

Nothing from the original is reproduced here; only sector numbers, sizes and structure numbers. Sector = 512 bytes, image offset = sector * 512 in `Disk.1`. Code: `src/audio/` (`tracks.ts` locates and unpacks, `modplayer.ts` parses and mixes, `webaudio.ts` outputs, `music.ts` is the API). Test: `test/music.mjs`.

## Where the music is (VERIFIED)

The game has four tracks, numbered 0..3 by the load table at `$14E8` of the game image (`game-proper.md`, 4 entries of 10 bytes: flags word, first sector, last sector, packed-buffer address). All four are on `Disk.1` (not on `Disk.2` or `disk.4`), packed with the byte LZ/RLE stream of `picture-lz.md` (`unpackLz`), one stream per sector range, no extra header. Unpacked they are plain ProTracker `M.K.` modules:

| Track | Sectors | Unpacked | Song length | Patterns | Samples used / looped / finetuned | Duration to first wrap |
|---|---|---|---|---|---|---|
| 0 | `$4AD`-`$59A` | 160,170 | 15 | 15 | 3 / 0 / 0 | 153.6 s |
| 1 | `$59B`-`$617` | 103,956 | 55 | 33 | 12 / 2 / 3 | 512.0 s |
| 2 | `$618`-`$6EB` | 159,822 | 46 | 31 | 15 / 1 / 0 | 359.7 s |
| 3 | `$3C3`-`$4AC` | 160,028 | 55 | 34 | 19 / 4 / 0 | 430.1 s |

Load-table flags words: `$103`, `$203`, `$102`, `$103` (tracks 0..3). **VERIFIED (static, `sfx.md` "The play routine `$11B4`")**: the loader copies the word to `$1582`; while music is active (bit 1 of `$1581`) the effect starter `$11B4` reads its high byte (`$1582`) and low byte (`$1583`) as the two Paula channels a sound effect may take (channel timer words at `$1518 + 2 * ch`; the first free one wins, both busy drops the request). The four words therefore mean channels (1, 3), (2, 3), (1, 2) and (1, 3). The module voice on the channel an effect takes is silenced for the effect's duration (player commands 7/8) and restored afterwards. This replaces the earlier "HYPOTHESIS: sound-effect channel arbitration"; the remake side is `Music.setChannelMuted()` / `SfxScheduler`. The flags are not needed for playing the module itself.

Track 3 is the module that the boot stage plays during the slide show (`graphics-and-music-blocks.md`, block C). The 20-byte title field of each module names it (the titles read as "title tune" for track 0 and as in-game tunes for tracks 1-3, HYPOTHESIS from the titles only: the in-game list offers all four equally as rows 0-3, see "Music-select flow"); read it at runtime with `Music.title(i)`, it is not stored in the repo.

Size check for every track: `1084 + patterns * 1024 + sum(sample lengths) = unpacked size` exactly (tested). All note periods are from the standard 36-note table (tested), every pattern cell uses sample numbers <= 24.

Effect census (cells with non-zero effect or parameter), identical set across tracks: 0, 1, 2, 3, 4, 5, 6, A, C, D, E (sub-effects 0, 9 and D only) and F. The F parameters are speeds only (3, 4, 6, 8, 12, 16), never BPM values (>= 32). Track 1 uses effect 5 (tone portamento + volume slide) and three samples with finetune, so the finetune period table matters there. Effects 7 (tremolo), 9 (sample offset), B, E3-E8, EA-EF do not occur in the shipped modules; they are implemented in `modplayer.ts` anyway.

## How the game plays it (VERIFIED structure, details HYPOTHESIS)

Loader at `$1100`-`$11B2` (game image loaded at `$1000`; file offset = address + `$28800` for the `Disk.1` image):

1. Track number `d2` (the low byte of the word `$8CFE`, the row of the music-select list; must be < 4, see "Music-select flow") is stored at `$1580`; the 10-byte table entry gives flags (`$1582`), sector range and packed buffer.
2. The sectors are read by the slave read hook `$93F8`, unpacked by `$8BEA` to `$43460`.
3. `jsr $158A` with `d0 = 0` (init, `d3 = 1` when byte `$910` is not `$32`, i.e. a 60 Hz machine) returns the tick address in `a0` (stored at `$1586`), then `d0 = 1`, `a0 = $43460` starts the module; bit 1 of `$1581` marks music active.
4. The vertical-blank code `$1264` calls the tick routine once per frame while that bit is set; when `$910` is not `$32` it skips every 6th call (counter `$1584`), so the tempo stays 50 Hz on a 60 Hz machine.

The routine behind `$158A` is the same family as the boot-stage player (`$7C8EC`): same nine-command front end (0 init, 1 play module, ...), same module layout, a NoiseTracker/ProTracker 1.x style replay routine with a 50 Hz tick. That the two copies behave identically is a HYPOTHESIS from the matching structure; the boot-stage copy was disassembled in detail (`graphics-and-music-blocks.md`), and the player in `modplayer.ts` follows that description.

## Replay rules implemented (from the boot-stage disassembly)

- Tick rate fixed at 50 Hz, speed (ticks per row) starts at 6, effect F sets `speed = param & $1F` when that is non-zero. No BPM. (`ciaTempo: true` switches to standard ProTracker tempo for other modules.)
- The first word (2 bytes) of every sample is zeroed; a sample with loop length <= 2 bytes is a one-shot, after which the channel is silent. A looped sample plays `[0, loopStart + loopLength)` once and then repeats `[loopStart, loopStart + loopLength)`.
- Song wraps from the last position to position 0 (restart byte ignored). `Dxx` break row is BCD (> 63 becomes 0), `Bxx` jumps, pattern loop `E6x`, pattern delay `EEx` as in ProTracker 2.x. Slides clamp to periods 113..856.
- Periods use the standard ProTracker table with 16 finetune rows; the note is looked up in row 0 and the value taken from the sample's finetune row (the table in the game image at `$2608` is the standard table; verified against `modplayer.ts`).
- Not emulated: invert loop (`EFx`, not used). Sound-effect channel ownership is modeled at the `Music.setChannelMuted()` / `SfxScheduler` boundary; the raw `$158A` player commands 7/8 are not exposed as tracker commands. The guest-controlled LED low-pass switch (`E0x`) is now modeled in `ModPlayer`; see the trace and limits below.

### E0x low-pass control (game-player static trace; output model approximate)

The game proper has its own player, separate from the boot-stage copy. Its extended-effect dispatcher at `$2130` indexes the table at `$2146`; subcommand E0 reaches `$2166`. That handler masks the parameter to bit 0, shifts it to bit 1, clears CIA-A PRA bit 1 at `$BFE001`, then writes the masked bit back. Module initialization at `$21D4` sets PRA bit 1, so it starts bypassed. Therefore E00/E02/... engage the switchable LED filter and E01/E03/... bypass it. This is a static Disk.1 disassembly result; no original audio capture was used to validate the output waveform.

`ModPlayer` now keeps the guest filter state and, by default, approximates the A1200 switchable LED path with three cascaded one-pole stages at a 5.5 kHz knee. `paulaFilter: "none"` disables that approximation for standalone renders while retaining the E0 state. The A1200 model and the 5–6 kHz LED-filter knee follow [WinUAE's audio model](https://github.com/tonioni/WinUAE/blob/master/audio.cpp#L2936-L3016); this implementation is not bit- or waveform-equivalent to Paula. Browser playback applies the switch once in the shared WebAudio output bus, so both module audio and SFX pass through it. No original audio waveform comparison has been made.

## Music-select flow (static trace, Disk.1; no emulator capture)

All addresses are game-image addresses (`game-proper.md`). This section supersedes the earlier "Track selection control" note, which read the word `$8CFE` as "the selected track" and the tutorial handler `$80C8` as "new scenarios start with track 0 selected". That was a misreading: `$8CFE` is the **row of the shared 10-row list** (a save/scenario slot row in modes 1-3, the track row in mode 4), and `$80C8` clears it for the scenario slot (`$8CFE` is copied to `$135C2`, the record index that `$8B02` uses), not for the music.

**The disk-menu screen.** `$7E52` loads picture 1 of the table `$8C8C` (sectors `$2CE`-`$2E4`): a black 10-row list panel at the left, nine 32 x 32 icon buttons at the right and a message area at the bottom (rendered locally to check the layout; nothing stored). The game proper does not start on the map: the init code at `$157AE` calls `$7E52`, which sets up this screen and falls into the disk-menu loop `$7EF6`, which runs until the exit button returns. The nine rectangles at `$8CB4` are {x0, x1, y0, y1} with the inclusive hit test `$5730`; the table index is `d2` of the dispatch `$7FE4`:

| `d2` | Rectangle (x, y) | Handler | Meaning |
|---|---|---|---|
| 0 | (208..239, 24..55) | `$85FE` | load game from a save disk (mode 2, `$13A`); picture: arrow out of a floppy |
| 1 | (256..287, 24..55) | `$856C` | save game (mode 1, `$138`; `$18A` while `$156AA` bit 3 is set); picture: arrow into a floppy |
| 2 | (208..239, 70..101) | `$8632` | load scenario from a scenario disk (mode 3, `$13D`); picture: plain floppy |
| 3 | (256..287, 70..101) | `$8314` | format a save disk (`$130`, Return confirms); picture: floppy with "!" |
| 4 | (208..239, 116..147) | `$1062` | music on/off (below) |
| 5 | (256..287, 116..147) | `$802C` | exit to the map (refused while `$156AA` bit 3, game over, is set) |
| 6 | (160..191, 24..55) | `$80C8` | **tutorial**: `$191`, scenario record 0, `$156AA` bits 7 and 2, money `$7A120`, then exit (not a generic "new game"; picture: graduation cap) |
| 7 | (160..191, 70..101) | `$1006` | **music select** (this section; picture: floppy with a note) |
| 8 | (160..191, 116..147) | `$10BC` | effects on/off (`$194` / `$195`; picture: "FX") |

The dispatch table is checked byte for byte against the user's Disk.1 by `test/disk-menu.mjs` (compare/branch chain at `$7FE4`, rectangle table `$8CB4`).

**Message areas (`$8462`, `$83A2`, `$84F4`, `$7EF6`; static trace).** There are two separate areas, both x 8, text via `$539E` (= erase `$51E6`, 6 scanlines, 37 bytes wide, then draw): the **prompt** lines at y `$A3` and `$AC` are printed by `$8462` (d0 = first, d1 = second; 0 skips a line) and cleared by `$84F4` (38 bytes wide), which `$82B8` calls; the **result** lines at y `$B5` and `$BE` are printed by `$83A2` (same d0/d1 convention; a zero argument leaves that line untouched, nothing is erased first) and end by storing 20000 (`$4E20`) in `$8CB0`. The loop `$7EF6` decrements `$8CB0` once per iteration while it is non-zero and, when it reaches 0, erases both result lines (`$7F0C`-`$7F68`, 37 bytes each). The unit is iterations of a mouse-polling busy loop, not frames, so the wall time is not known statically. `$82B8` never touches the result lines or `$8CB0`; `$1006` prints its prompt with `$8462` (y `$A3`); the handlers `$1062` and `$10BC` print with `$83A2` and d0 = 0, i.e. on the SECOND result line (y `$BE`), so a toggle message does NOT replace the list prompt. (An earlier version of this note and of the port drew the toggle messages over the prompt at y `$A3`; that was wrong.) The menu sets `$5D7A` to `$16D6A`; `$4F92` builds that five-plane, eight-row pattern by sampling byte column 19 (pixels 152..159) of rows 70..77 from the displayed picture. `$51E6` tiles that 8x8 patch across each erased strip with vertical phase `y & 7`. `DiskMenuScene` derives this tile from the decoded menu picture, applies the 38-byte prompt clears at setup/close and the 37-byte result clears at print/timeout. This is a static source match; no original menu screenshot comparison exists.

**Opening the list (`$1006`).** `$82B8` first closes any list (clears the mode byte `$938D`, the prompt lines and the ten row areas; result lines stay). If bit 0 of `$1581` (extra memory; the init code at `$156E4` sets it when `$904 != 0`, and the slave sets `$904`) is clear, message `$197` ("Music unavailable without expansion memory") is printed through `$83A2` (second result line, d0 = 0 as in `$1062`) and the list stays closed. Otherwise ten lines are drawn with the `$539E` font at x `$3A`, y `$20 + 9 * row`; row `n` is the 8-byte NUL-terminated string at `$1530 + 8 * n` (rows 0-3 are four short names, rows 4-9 are seven spaces); message `$190` (English: a "select a tune" prompt) is printed at x 8, y `$A3` (`$8462`); and `$938D = 4`. The remake reads the labels at run time from the game image (`readMusicLabels`) and the prompt from the string table; neither is stored.

**Row hit test and highlight (`$8132`, `$818C`, `$826E`).** The loop calls `$8132` on every iteration, so it is a hover test and not a click handler. With `$938D != 0` and x in `$38..$88`, y in `$20..$79` (inclusive), the row is `floor((y - $20) / 9)` = 0..9. If it differs from `$8CFE`, the old bar is restored (`$826E`, then `$821E` redraws that row's text), the new row is stored in `$8CFE`, and the bar is drawn (`$818C`: 11 bytes = 88 pixels wide from x `$38`, six scanlines from y = `$20 + 9 * row`, bit planes 0-2 set and 3-4 cleared = palette index 7 of the picture; `$821E` then draws the row text on top). Outside the bounds the bar is cleared and `$8CFE = $FFFF`. In mode 4 the text `$821E` draws comes from `$1530 + 8 * row`; in modes 1-3 it comes from the header records at `$8F96 + $40 * row`.

**Click, confirm, cancel (`$7F72`-`$7FE0`).** The loop reads the mouse edge from `$50B2`. **The right button is ignored** (`$7F80`: `bne $7EF6`). A left press first hit-tests the nine icons: a hit calls `$5948` (flip plus the id 4 click, `sfx.md`) and returns to the loop, and the icon's action runs on the **release** (`$7F96`-`$7FA6`, then `$7FE4`). A press that hits no icon calls `$2E52`, which busy-waits until the left button is released (`btst #6,$BFE001`) and then, if `$8CFE >= 0`, calls `$87DC`. The hover test does not run during the wait, so `$8CFE` is the row of the press: **the action runs after the release, on the row the press began on, wherever the pointer is by then.** `$87DC` with `$938D = 4` branches to `$8A42`, which is `bsr $110A` then `bsr $82B8`. List rows are not buttons: no click is requested for them.

**Track loader (`$110A`).** `cmpi.b #4,d2` on the low byte of `$8CFE`: a row below 4 loads; any other row (4-9) calls `$82B8` and goes back to the loop **without touching the music**. That, or pressing an icon, is the only way out the original offers. Loading sets bit 4 of `$1581` (loading), runs `$8A4C` (insert-disk check; trivial under WHDLoad), **clears bit 1 (music active: the tick stops)**, clears bit 4, writes DMACON `$F` (all four channels off), stores the row at `$1580`, copies the table flags word to `$1582`, reads the sector range through `$93F8`, unpacks it with `$8BEA` to `$43460`, calls `$158A` with `d0 = 0` and then `d0 = 1`, and sets bit 1. **There is no comparison with the track that already plays**: selecting the playing track reloads and restarts it from its first row; nothing is faded. The disk read has no modelled duration (immediate under WHDLoad). After `$110A`, `$82B8` closes the list: the player is back in the **disk menu** (icons), not on the map; the exit icon (5) leaves it.

**What starts and keeps music.** Among absolute-long references in the game image there is exactly one caller of `$110A` (the `$87DC` dispatch to `$8A42`), exactly one writer of the track byte `$1580` (`$1142` in the loader; `$1088` only reads it) and no `jsr $158A` with `d0 = 1` outside the loader (the other `$158A` callers are the loader's init call and the effect commands 7/8 of `$11B4` and the timers). The image default is `$1580 = $FF`, `$1581 = $04` (no track loaded, effects on, music inactive). So the game proper starts **silent**, and starting a new scenario (`$80C8`), loading a game (`$87DC` mode 2, `$8AF4`/`$8B02`: scenario and state data only) and a Disk.4 slot do not start, stop or change the music. The selection is not part of any save: `$1580`/`$1581` lie outside the saved areas A (`$39E3A`, 37,376 bytes) and B (`$13034`, 5,632 bytes). The boot stage's module is faded out before the game proper starts (`graphics-and-music-blocks.md`).

**Music on/off (`$1062`; traced statically, ported, see "Remake lifecycle").** Every message below is printed through `$83A2` with d0 = 0: second result line, y `$BE` (see "Message areas"). Bit 0 of `$1581` clear: message `$197`. Bit 1 clear (inactive): `$1580 < 0` prints `$196` ("No music loaded"); otherwise bit 1 is set (the same loaded module ticks on from where it stopped) and `$192` ("Music on") is printed. Bit 1 set: clear it, DMACON `$F` off, print `$193` ("Music Off"). The state is the pair (`$1580` = selected track, bit 1 = active): switching off keeps `$1580`, and the sound-effect starter `$11B4` reads bit 1 (`sfx.md`), so a switched-off track still selected leaves all four channels to effects. The track loader `$110A` clears bit 1 while loading and sets it again afterwards, so picking a row (rows 0-3) while paused starts that track and leaves the music active.

The list and message use colour 1 (static call-path trace in game-text.md section 3); whether the module titles match the labels (`Music.title(i)` reads the module's own title field; the list labels are the `$1530` strings); and one original quirk that is not reproduced: a stale `$8CFE` suppresses the first bar when the pointer enters the row it still names (the loop resets `$8CFE` to -1 whenever the pointer is outside the list or the list is closed, so it needs an action that leaves `$8CFE` set, rare). CORRECTION of an earlier reading: `$826E` does not restore "11 scanlines per row". `$51E6` takes d2 as a byte width (11 bytes = 88 pixels, the bar width) and always erases 6 scanlines. The pressed icon look (`$5948` -> `$59A0`) is a 32 x 32 flip of plane 3 and is now drawn; see sfx.md "Disk menu" and screens.md section 10.

## Remake lifecycle (`src/game/game.ts`, `src/game/disk-menu.ts`, `src/game/music-select.ts`; tests `test/disk-menu.mjs`, `test/music-select.mjs`, `test/music-pause.mjs`, `test/game-music.mjs`, `test/button-sound.mjs`, `test/disk4-scene.mjs`)

Implemented from the static evidence above, nothing more:

- **One scene for the whole disk menu.** `Game.openDiskMenu()` (stage `disk`) builds a `DiskMenuScene` on the original picture (`DISK_MENU_PICTURE`, sectors `$2CE`-`$2E4`): the landing page is the untouched picture (no text, closed black list panel); the shared list (icon 7) is a state of the same scene, not another stage or picture. The earlier text-list `MenuScene` landing page and the separate `MusicSelectScene` stage are gone. `music-select.ts` keeps the list geometry, `toggleMusic` and the string numbers; `disk-menu.ts` owns pixels, icons, message areas and input. The scene reports `track`, `listClosed`, `icon` and `remake` results; `Game` runs the handlers.
- **Press and release.** A press on any of the nine rectangles (`$8CB4`, inclusive) draws the pressed look (32 x 32, colour ^ 8 = plane 3, `$59A0`) and requests the id 4 click exactly once (`onButtonPress`, which `Game` binds to `sfx.play(SFX.CLICK)`; holding repeats nothing, `$59C8` on the release is silent). The release restores the picture and the action runs for the icon RECORDED at the press, wherever the pointer is by then; a press that began outside every rectangle and ends on one does nothing. The click that opened the menu (still held) is ignored.
- **Selection.** A left press on a list row remembers that row, the action runs on the release (as `$2E52` does). Rows 0-3 call `Music.play(track, true)`: the module always restarts, also when it already plays (`$110A` has no same-track test). Rows 4-9 only close the list. In both cases the scene closes the list (`$82B8`) and the menu stays on screen (it does not go to the map); list rows are silent. With the list closed the panel does nothing (the hover test needs `$938D != 0`).
- **Icons.** 4 music on/off, 5 exit to the map (refused while the sim reports game over, `$156AA` bit 3), 7 opens the list (with no `Music`: `$197`, list stays closed), 8 effects on/off, 6 starts the tutorial (scenario 0, tutorial and no-unit-bonus flags, money `$7A120`). Icons 0-3 are the save-disk family (load, save, scenario, format) and need floppies: the remake maps 0 / 1 / 2 to its own pages (`LOAD GAME - REMAKE SLOTS`, `SAVE GAME - REMAKE SLOTS`, the scenario list; save while game over prints `$18A`, with a Disk.4 session it opens the remake menu where the disabled entry explains why) and prints a REMAKE note for 3. These mappings of 0-3 are the remake's substitutes, not original behaviour.
- **Effects icon (`$10BC`, icon 8)**: the click is requested on the press with the state it had; the release toggles `Sfx.setEnabled` and prints `$195` ("Effects off.") when it was on, `$194` ("Effects on.") when it was off, on the second result line. Without an `Sfx` there is no flag to toggle: nothing happens.
- **Music on/off icon (`$1062`, icon 4)**: the action runs on the **release** (`toggleMusic`), the list **stays open** if it was open, and the string goes to the second result line (y `$BE`; the prompt at y `$A3` stays): active -> `Music.setActive(false)` and `$193`; inactive with a selected track -> `Music.setActive(true)` and `$192` (no `play`, no reload, no restart); inactive with nothing loaded (`current < 0`) -> `$196`, no state change. With no `Music` at all `toggleMusic(null)` yields `$197`. The strings are read from the user's own string table at run time (`GameStrings.get`, never stored). Result lines disappear after `INFO_LIFETIME_FRAMES` (HYPOTHESIS: 50 frames for the traced 20000 loop iterations); each new result restarts the countdown, closing the list leaves them alone.
- **Remake-only affordances.** The right button is ignored by the original loop. The remake uses it: with a list open it closes the list (no track change); on the landing page it opens the REMAKE MENU page (`MenuScene`, stage `remake`: remake save, remake load, scenario list, experimental Disk.4, back), which is deliberately not drawn on the original picture and titled as not original. Right click on any remake page returns to the disk menu. The remake slots and Disk.4 are reachable only from there (and icons 0-2 for the remake pages); Disk.4 sessions are still refused by the native-save provenance policy.
- **New scenario, remake load, Disk.4 activation**: never start, stop or change a track (no original code path does). The game starts silent until the player picks a track; the earlier remake behaviours "new scenario starts track 0" and "load/Disk.4 with nothing playing starts track 0" had no evidence and are gone. The selection is not stored in the remake save (neither is it in the original's).
- **Language/intro tune**: the remake still plays track 0 on the language screen (HYPOTHESIS, module title "title tune"; the original boot stage plays its own module there). It is faded out (1 s) at the first map entry, standing in for the boot-stage fade before the game proper starts (`introTune` in `Game`); a track picked in the list is never faded by a scenario start.
- **Pause API (`src/audio/music.ts`)**: `Music.setActive(false|true)` detaches/re-attaches the same `ModPlayer` to the `WebAudioSink` (the sink renders silence meanwhile; the player is not stopped, reconstructed or advanced, so song position, tick phase, speed and every channel's sample position continue exactly; `test/music-pause.mjs` compares the resumed PCM with an uninterrupted render sample for sample). `Music.current` is the selected/loaded track (kept while paused, -1 only before the first selection or after `stop()`), `Music.active` is the music-active bit (`current >= 0` and not paused); they are separate. `play()` (the loader) always leaves the music active, also when the track is the paused one and `restart` is false (then it continues from the pause position); `stop()` and `dispose()` clear the pause with the selection. `fadeOut()` no longer arms a wall-clock timer: it ramps the sink gain and the music stops when a block tick (`Music.onBlock`, AudioContext time) passes the end of the fade; a track load or `stop()` cancels it, and a suspended context does not advance it (with no audio graph yet it stops at once). Every state change that the original makes with DMACON `$F` is announced to `Music.onChange` listeners (`dmaOff`): `setActive(false)`, a track load (`play` that loads or restarts) and `stop()`/`dispose()` with a loaded track; `setActive(true)` and the continue-without-reload form of `play()` only set the active bit (`dmaOff` false). The effect model listens to these (sfx.md "Channel ownership"); the remake's own transitions stay as above.
- **Not ported / not verified**: (a) the module-side result of a DMACON `$F` write during `$1062`/`$10BC`. The traced effect-side behavior is implemented: the write cuts sounding effects while timers continue, and `$10BC` clears timers but holds queued entries (sfx.md "Channel ownership", `test/audio-ownership.mjs`). The player tick (`$1B1A`-`$1B22`) re-asserts bits from `$250C`, and `$F` does not clear that word, but the audible result when a channel resumes still depends on Paula DMA behavior. The port resumes the paused `ModPlayer` bit-exactly; no original capture verifies whether a looped sample restarts at its loop pointer or how a one-shot behaves. (b) The wall time of the result-line countdown (see above). (e) `$7F80`: the original ignores left-button edges while the right button is held; the port does not. (f) The eclipse palette swap `$11024` around the menu (`$7ED4`, `$8040`) and the disk-insert checks (`$8A4C`, `$8A5A`), which are no-ops under WHDLoad or have no remake counterpart. (g) The remainder of the tutorial start `$866E`: the remake relies on the scenario start's own state. Static trace only; no emulator capture of the menu.

The original ignores the right button; the remake keeps right-click navigation as a remake-only affordance. To preserve the traced `$7F80` ordering, left-button press/release edges are consumed while right is held, so simultaneous input cannot also activate an icon or row (`DiskMenuScene.update`, `test/disk-menu.mjs`). This rule is statically traced and synthetically checked, not compared with an original interaction capture.

## Paula model in `modplayer.ts`

- Channel rate = 3,546,895 / period samples per second (PAL colour clock), 4 channels, 8-bit signed samples, volume 0..64, master volume 0..64 (the original scales `vol * master * 25 / 1600`, i.e. 64 = unchanged).
- Amiga panning: channels 0 and 3 left, 1 and 2 right; `separation` 0..1 (default 0.5) mixes the far side in. `interpolation: "nearest"` gives raw sample-and-hold, default `"linear"` (periods >= 113 give < 31.4 kHz source rate, so linear interpolation never aliases at 44.1/48 kHz output).
- The mixer is sample accurate: each 50 Hz tick is `sampleRate / 50` frames with the fractional remainder carried, so output does not depend on buffer sizes (tested).

## API

```ts
const music = createMusic(disk1, disk2);   // src/audio/music.ts; modules decoded lazily, disk2 unused
music.play(0);                              // track 0..3, loops; call from a click/key handler the first time
music.fadeOut(1.5); music.stop(); music.setVolume(0.8);
music.setActive(false); music.setActive(true);  // button $1062: pause / continue at the same position; music.current (selected) vs music.active (audible)
```

`ModPlayer` (`src/audio/modplayer.ts`) is the DOM-free core: `parseMod(bytes)`, `new ModPlayer(song, { sampleRate })`, `render(left, right, offset?, count?)`, `ModPlayer.duration(song)`. Output goes through a `ScriptProcessorNode` (`webaudio.ts`); browsers keep an `AudioContext` suspended until a user gesture, so `play`/`resume` must be reached from one.

## Open

- Which track, if any, the original ties to a screen or event: none exists in the game image (the only starter is the list, see "What starts and keeps music"), so the remake's language-screen track 0 is the only unevidenced assignment left (module titles only). The state of the boot-stage player at the hand-off to the game proper is taken from `graphics-and-music-blocks.md` (faded out), not re-traced.
- The sound-effect channel sharing is no longer open: the flags words are channel numbers (VERIFIED, `sfx.md`); sound effects are separate sample playbacks on the same Paula channels and not part of the module. Ownership, interruption (music off, track reload, effects off) and hand-back are modelled from the 2026-11-07 static re-trace (`SfxScheduler`, `Music.onChange`/`onBlock`/`setChannelMuted`); the remaining module-side approximations (resume from the loop pointer, effect tail after an expiry, block-granular muting) and the missing capture are listed in sfx.md.
- Music on/off (`$1062`) is ported from the static trace (see the not-verified list under "Remake lifecycle": DMACON side effect, countdown wall time); the countdown length is not captured.
- The module playback has not been compared sample-for-sample with an emulator capture; correctness is checked structurally (periods, timing, pitch of synthetic modules) and by rendering without NaN.
