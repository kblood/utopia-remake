# Arkitektur – Utopia-motor

Målet er at dekompilere og genskabe Amiga-spillet Utopia som en selvstændig, spilbar motor. Motoren indeholder ingen spildata; spilleren leverer sine egne originale filer, som motoren læser lokalt. ScummVM er ikke et mål eller en afhængighed. ADF- eller HDF-input kan bruges, hvis det gør indlæsning af brugerens spilfiler praktisk, men kun når det konkrete format og den konkrete udgivelse er identificeret og understøttet.

## Princip

1. **Motoren** (denne repo) indeholder kun egen kode: loaders, decodere, spillogik og renderer.
2. **Originaldata** leveres af brugeren fra egen kopi af spillet. Første understøttede profil er WHDLoad 1.2 (0757) udpakket filstruktur. ADF/HDF kan tilføjes som alternative inputprofiler efter verifikation. Dataene ligger lokalt og er gitignored.
3. Ved start scanner motoren mappen, genkender filnavne og størrelser og validerer derefter signaturer og erklærede filområder, før dataprofilen startes.
4. Ingen originale filer committes, udgives eller indlejres i build-output.

## Lag

| Lag | Ansvar | Kilde |
|---|---|---|
| `io/` | Afgrænset læsning af de understøttede WHDLoad-filer og XPK/MASH-dekodning af `disk.4`; OFS/FFS-montering er ikke implementeret | Egen kode |
| `formats/` | Decodere for grafik (bitplanes), tiles, kort, lyd og tekst | Egen kode, baseret på observation |
| `detect/` | Genkender spilversion ud fra filnavne og -størrelser (`src/data/detect.ts`, kun metadata; `disk.4` er valgfri). Validerer derefter de indlæste bytes (`src/data/profile-input.ts`, `src/startup.ts`). Ingen hashes af originalt indhold gemmes eller committes | Egen kode |
| `game/` | Spillogik: kort, økonomi, AI-ture, tilstande | Clean-room-specifikation i `notes/` |
| `render/` | Canvas 2D-renderer med 320×256-buffer og Amiga-lignende palet | Egen kode |
| `audio/` | Afspilning af decodet musik og effekter | Egen kode |
| `ui/` | Menu, input, skalering | Egen kode |

## Arbejdsgang for et nyt dataformat

1. Find filen og dens format i `original/` (magic bytes, størrelse, struktur).
2. Skriv en decoder i `formats/`, der kan køre på originalfilen lokalt.
3. Verificér decoderen mod en emulatorkørsel (WinUAE eller Copperline). Skærmbilleder eller hukommelsesdumps er referencen.
4. Dokumentér formatet i `notes/formats/<navn>.md` med observationer, ikke med kopieret kode.
5. Tilføj en test, der kører på den lokale fil, hvis den findes. Testen springes over, hvis filen mangler.

## Kendte input og status (WHDLoad 1.2 / 0757)

- `Disk.1` (970 752 bytes) har `DOS\0`-signaturen. Indlæsningen læser den direkte; størrelsen er ikke en standard-ADF.
- `Disk.2` (983 040 bytes) indeholder scenariedata; `UTOPSCEN`-headeren ligger ved `$3C0`, og de ti poster deklarerer deres ressourceområder.
- `disk.4` (656 bytes) begynder med `XPKF`, så det er XPK-pakket (MASH). Den udpakkes af `tools/xpk_mash.py` og af den afgrænsede TypeScript-dekoder `src/data/xpk-mash.ts` (bruges af den eksperimentelle Disk.4-aktivering via `parseDisk4Input`); se [formats/xpk-mash.md](formats/xpk-mash.md).
- `Utopia.Slave` er WHDLoad-slaven. Den er en nyttig kilde til filnavne og offsets, men den validerede loader kontrollerer foreløbig kun tilstedeværelse og størrelse; slave-indholdet analyseres ikke ved opstart.
- `Hints`, `Introduction`, `Manual` og `ReadMe` er tekstfiler.

### ADF og HDF

- Der findes to lokale ADF-billeder. Disk B er byte-for-byte lig de første 1760 sektorer af WHDLoad `Disk.2`; Disk A afviger i spilbilledets sektorer `$14C-$208`. De er derfor ikke direkte ækvivalente med den nuværende WHDLoad-profil. Se [utopia-disks.md](formats/utopia-disks.md).
- De fundne HDF-installationer er undersøgt, men de kendte Utopia-stier indeholder ikke udpakkede spildata. HDF-understøttelse er ikke implementeret.
- Praktisk prioritet: behold den fungerende WHDLoad-indlæsning som baseline. Tilføj ADF/HDF-indlæsning, når en bestemt tilgængelig kopi er valid og kan identificeres; emulatoren kan stadig bruges som reference til adfærd.

## Input boundary: recognition, validated availability, runtime compatibility

Three claims of increasing strength; only the first two are implemented, and only for the WHDLoad 1.2 (0757) profile.

1. **Format recognition** (`detectProfile`, `src/data/detect.ts`): file names (case-insensitive, first match wins) and sizes of `Disk.1`, `Disk.2` and `Utopia.Slave`. `disk.4` is optional with no size requirement, so a folder without the save seed is recognised. No content is read.
2. **Validated resource availability** (`validateProfileBytes`, `src/data/profile-input.ts`, driven by `startFromFiles` in `src/startup.ts`): after recognition the bytes are read and checked before `createMusic`, `createSfx` or `Game` exist. Checks: `Disk.1` starts with `DOS\0` and matches the profile size; `Disk.2` matches the profile size, covers the two header sectors at `$3C0`, carries the `UTOPSCEN` magic, and every one of the ten sprites/tiles/descriptors/map/block/intel/text(4) ranges declared by the ten scenario records has `first <= last` and ends inside the file. Failures are typed `InputError`s (`missing-file`, `file-size-mismatch`, `read-failed`, `disk1-too-small`, `disk1-signature`, `disk2-header-truncated`, `disk2-signature`, `scenario-range-inverted`, `scenario-range-out-of-bounds`) with file, scenario and field context; malformed or truncated files never throw. `disk.4` is carried through only if readable (an unreadable one is a warning); its XPK/area content is validated later, when the disk menu opens it (`parseDisk4Input`). Not checked: Disk.1's internal sector tables (picture, tile sheet, music and sound ranges), tile descriptor contents, and anything inside the ranges beyond their bounds. Bounds are against file size only; the range semantics come from the verified loader notes in `formats/game-proper.md` section 6. Content is neither hashed nor stored.
3. **Proven runtime compatibility**: not established by either check. Passing validation means the declared resources are present and in bounds, not that the game runs like the original on that copy. The ADF images remain unsupported: the local ADF A needs an emulator trace before its differing game-image sectors can be accepted, so the validator deliberately does not relax the `Disk.1`/`Disk.2` layouts.

## Remaining verification gaps

The engine reads the player's WHDLoad 1.2 (0757) files for graphics, audio, text, maps and simulation data. That establishes usable formats, not broad fidelity. Three narrow live-original comparisons exist: one tank route, one November production transition and one RAM-staged invasion sequence; each is limited to its captured state and exclusions. The invasion replay passed its compared groups from queued wave through gun-kill and the following pass, but its staged baseline has an inconsistent object count relative to its non-empty records, so it does not establish ordinary-play combat parity. No audio waveform or frame/pixel comparison exists, and the original `$2DCC` routine remains an isolated model rather than the engine's generator because caller D0, CIA TOD and seed initialization are not fully established. Remaining engine work includes broad connected-play comparison, machine-dependent timing, unresolved state fields and screen interactions, full original Disk.4 post-load/save compatibility, and presentation/audio parity. See the relevant format notes for evidence and limits. The browser loader recognizes only the unpacked WHDLoad 1.2 (0757) profile; it does not mount ADF/HDF/IPF images or recognize other releases. The local ADF and HDF copies are not currently drop-in substitutes for that profile.

**Audio ownership (`src/audio/sfx-scheduler.ts`, `sfx.ts`, `music.ts`, `webaudio.ts`).** `SfxScheduler` is a DOM-free, frame-stepped model (50 Hz) of the original's effect state (`$1520` queue, `$1518` timers, the player's per-channel enable word, the music-active and effects-enabled bits). Every change is an explicit call with its frame (`request`, `musicChanged`, `setEnabled`, `advanceTo`, `dispose`) and every consequence is an event (`queued`, `drop`, `start`, `cut`, `end`) or readable state (`moduleEnabled`); it owns no timers and calls nothing back. `createSfx` is a projection: one cancellable `AudioBufferSourceNode` per queued or sounding voice, scheduled on `AudioContext.currentTime`, plus a diffed mirror of the module-ownership words into `Music.setChannelMuted`; the model is advanced by each call and by the music's block tick (`Music.onBlock`, ScriptProcessor `playbackTime`), and music transitions arrive through `Music.onChange` (`dmaOff` = the original's DMACON `$F`). `Music.fadeOut` ends on the same block tick; no `setTimeout`/`setInterval` remains in `src/audio`. `Sfx.dispose()` cancels all nodes, returns muted voices, detaches the hooks and makes later calls inert. Traced behaviour (static, Disk.1): command 7 at the request, command 8 only under active music at the expiry, DMACON `$F` cuts sound but not timers, effects off clears timers and holds the queue (sfx.md "Channel ownership"). Evidence is static trace plus synthetic tests (`test/audio-ownership.mjs`, `test/sfx.mjs`, `test/music-pause.mjs`); no original audio capture, so no waveform or timing parity. Remaining approximations: block-granular muting, no effect tail after expiry, bit-exact module resume instead of a loop-pointer restart, and the "never handed back" cases reproduced from the code reading alone.

The module also exports the page lists with the `$B2AA` research substitutions and blanked slots (`menuTiles`), the `$E9E2`/`$EA3C` rectangles (`menuHitIndex`) and the placement of 1x1 and 2x2 buildings (`tilePlacements`, `itemPlacements`), so hit testing and drawing cannot diverge. Rendering writes no game state, world, disk or tile data. The remake preserves the last page (`$156B0`) and renders the destination page on release; the original performs 14 strip erases synchronously between VBL waits, with no per-strip frame animation established. In build mode `Controls` redraws the committed building at `(272,52)`, following `$6B10`. Colour 1 is statically supported by `$4D96` resetting `$156AB` before the map input poll. Evidence is a static trace of the local Disk.1 image (`notes/formats/building.md`, "Menu panel rendering") with synthetic and local-data pixel checks in `test/build-menu.mjs`; there is no running-original screenshot comparison, so art parity is not claimed.

**Runtime checkpoints (`src/game/checkpoint.ts`, schema 4).** An opt-in, read-only observer for original-vs-remake comparison: `MapScene.enableCheckpoints(options?)` records a bounded in-memory list of deep-frozen, JSON-serializable `RuntimeCheckpoint`s, one per completed main-loop cycle, taken after redraw, date/periodic work and input poll; `captureCheckpoint()` takes a one-off "manual" one. Fields: video update / pass counters, `$144C9`, day timer, date, pending period bits, pause, queued day, economy / population / job-pool / stock counters, object records and construction sites, occupancy-bit cells, the 99 tank, 60 + 30 enemy and 40 ship/missile fixed slots (position, offsets, hp, mode, targets, reservation pointer, crusher and ship extras) and the queued messages / events. It writes nothing, draws no RNG, calls no hook, never persists or logs (only the caller's `onCheckpoint` callback sees the data) and carries no asset bytes or hashes; the RNG state and message text are not captured. Exact boundary, field list and limits: [formats/runtime-checkpoints.md](formats/runtime-checkpoints.md). `test/checkpoint.mjs` covers stable, copy-safe snapshots and loop equivalence with capture on (the `MapScene` part needs the local Disk.1/Disk.2); bounded comparisons with the running original include the tank slice and November production replay; neither establishes broad combat parity.

**Alien apparition drawing (`src/game/alien-sprite.ts`).** `readAlienApparition(state)` is a read-only adapter over active type-19 record `$144A8..$144AD`; `MapScene` installs it as `ObjectLayer.apparition`, and `ObjectLayer.drawMap` blits it as a sorted draw-list entry with the `SpriteSet` masked frame decoder, anchor (bottom row `anchorY - 1 + dy - 13`: `$3604` lowers the type-19 y anchor by 13), and signed pixel offsets `+3`/`+4`. The static `$3694` trace establishes the frame-selected edge behavior: for frames 0..3, the last column always admits frame 0 and hides frames 1..3 only for positive `dx` or `dy`; the last row admits frames 0..2 and hides frame 3 only for positive `dy`. The shared per-pixel right clip is documented in map-rendering.md 7.3. Drawing does not advance animation, RNG, occupancy or effects; the alien is an admitted sorted entry that never opens the redraw gate and blocks picking without being an order target. Same-cell order is the traced `$4860` sort (map-rendering.md 7.2b). Artwork/palette parity remains unverified; there is no emulator pixel comparison. Checked by `test/alien-sprite.mjs`.

**Meteor drawing (`src/game/meteor-sprite.ts`).** `readMeteor(state)` is the same kind of read-only adapter over the active type-21 record `$1449C..$144A2` (`+3`/`+4` signed offsets, `+5` frame, `+6` signed byte that is both the countdown and the drawing lift). `MapScene` installs it as `ObjectLayer.meteor`, polled at draw time; `drawMap` blits it as a sorted draw-list entry with the existing masked `SpriteSet` frame, bottom row `anchorY - 1 + dy - lift` (no alien-style extra adjustment), the existing window rule and the shared statically traced per-pixel right clip, including the x=255 scratch-alias quirk (map-rendering.md 7.3). **Draw list and effect slots (`src/game/draw-list.ts`, `src/game/effect-pool.ts`, `src/game/objects.ts`).** `draw-list.ts` is the pure part of the traced original: the `$333A` source order and flags, the order key `63 - painterSeq` (`$7BA8`), the literal `$4860` selection sort (`sortDrawList`, deliberately not stable) and the single cursor with the redraw-gate block (`DrawCursor`). `ObjectLayer` feeds it: `admitted()` builds the `$3694`-admitted entries (own tanks, ships/missiles, enemy ground, enemy air, effect slots, alien, meteor, then the untagged `extra` list as an explicit approximation), `drawList()` sorts them globally, `gate()` computes the redraw gate (own tank/ship, visible animated cell, invention bit 17), `beginFrame()` returns a `FramePass` that owns the cursor and the neighbour-tile marks of one redraw, and `drawMap()` paints tiles, sorted entries and pins; `pickables()` lists the same sorted entries, with enemies, effects and the specials as non-target obstacles. Hovering a valid unclaimed map cell alternates descriptor 58 in place of its tile, following `$6568-$658E`; a cell already drawn as a neighbour skips the selection toggle. `MapScene` also selects the `$4AA4` pointer graphic on a live map-cell hit and `$4A74` otherwise, following `$2FBA`; both graphics are decoded from user Disk.1. These presentation choices are not written into the saved map. `EffectPool` is the original's 30 fixed effect slots (first free slot, slot-local expiry, count word derived); native saves store all 30 slots since version 8 and runtime checkpoints since schema 4. Evidence: static Disk.1 trace and synthetic/local-data tests (`test/draw-list.mjs`, `test/map-loop.mjs`, `test/pointer.mjs`, `test/save.mjs`); no emulator frame comparison. The gate is reset once per normal `$333A` cycle, populated by admitted objects and `$6936` animated cells, then snapshotted before map redraw and retained across intervening video redraws; modal iterations retain the prior value, and an initial pre-pass frame computes it live. The static snapshot placement is now traced; exact video-frame visibility, pointer hotspot alignment, paused-meteor control flow, artwork parity, slot numbers of effects migrated from saves of versions 6/7, and the approximate `extra` list remain open (map-rendering.md 7.2b/7.4, units.md section 6).

**Map background restore (`src/game/map-background.ts`).** Port of the original per-pass background rebuild `$16012` and its mask generator `$15F9A` as pure functions over indexed pixels: `generateMapPattern()` re-runs the 63-state shift machine (64 x 8 longs at `$14640`, plus the unused forward stream at `$14E40`), and `restoreMapBackground(initial, current)` rewrites rows 0..23 (texture with swapped halves), rows 24..87 (texture ANDed with the pattern) and, from the initial picture, rows 89..159 and the x 256..271 / rows 47..96 column, leaving row 88 and everything else as in `current`. `MapScene` maintains two persistent pixel buffers, applies the restore and draws on scheduled main-loop passes, and keeps the displayed bitmap between passes. Modal menu redraws do not swap buffers or write them back (the pre-menu frame returns on exit); the remake's per-pass overlays (button flips, message line/log, side preview) are reset from the picture before drawing since `$16012` never restores those areas; the queued day tick runs inside the top-bar draw, before the date text (`$4D1C`). The texture and snapshots are taken from the player's decoded picture, nothing from the original is stored. This implements the statically traced cadence; browser pass timing and visual parity remain unverified. Tests include asset-free vector checks (`test/map-background.mjs`) and a live-scene buffer check (`test/map-loop.mjs`). Details and limits: map-rendering.md section 9.

**Remake save/load (`src/game/save-session.ts`, `src/game/save.ts`).** `captureSession(parts, scenario)` reads the live `MapScene` members (`world`, `sim`, `loop`, `objects.units`, `enemies`, `objects.markers`, `objects.pool`, `scrollRef`) into a validated `SessionSave` (version 9): state image, map words, cell flags, object records, the 99 tank, 60+30 enemy and 40 ship/missile fixed slots (holes kept) with the raw `+$16` pointer of every enemy slot (`EnemySystem.groundFlagPointers` / `airFlagPointers`, free slots included: the pointer belongs to the slot, survives death and reuse, and a death releases the cell it names, enemies.md 3b), ship extras, reservation cells and missile enemy-slot references, legacy gun-countdown compatibility field and launch target, `$144C9` clock, loop cadence/phase and pending modal-return pass, system flags, pause, queued day, lights, alien/meteor/spawner, simulation RNG, solar-phase RNG, deterministic hardware-approximation counters, pins, the 30 fixed effect slots (`effectSlots`, holes kept; gameplay-relevant because capacity decides whether a combat explosion allocates and so whether the killed enemy's occupancy bit is cleared, and because the first-free slot and slot order decide draw order; outer `null` = no object layer, 30 `null`s = empty pool) with the durable `effectSlotsAssumed` flag, and view. Versions 6 and 7 stored a dense list: their records are all kept in slots 0..n-1 with an explicit slot assumption (`ReadResult.effectSlotsAssumed`, label `FX SLOT UNK`, carried through later saves until the pool drains), not an exact continuation; versions 2-5 never stored effects and migrate to an empty pool as a lossy compatibility assumption (`ReadResult.effectsAssumedEmpty`), not an exact continuation. Capture refuses a non-empty untagged `ObjectLayer.extra` list (`unsupported-state`). Versions 2-6 never stored the raw enemy pointers: occupied slots derive theirs from the saved reservation cell, free slots get 0 (a documented assumption, `ReadResult.enemyPointersAssumed`; slot labels from `slotWarning()`: `FX UNKNOWN`, `PTR UNKNOWN`, `FX/PTR UNK`), also not exact. `$142A6` uses elapsed years; version-2 and version-less remake saves convert the previous absolute year on read. `restoreSession` validates, builds all records detached and only then commits, copying into the live shared `cells`/`cellFlags` arrays (identity and the unit/enemy/world sharing are kept); `Game.loadFromSlot` additionally creates the target scene first and swaps it in only after a successful restore. A refused save or load (`Game.lastSaveError` / `lastLoadError`) opens the disk-menu stage `sloterror` over the untouched map: typed code, wrapped message, `RETRY SLOT`, `CHOOSE ANOTHER SLOT`, `DISK MENU`, `BACK TO GAME`; `slotSummaries()` reports `unavailable` (list label `STORAGE OFF`) when localStorage is missing, and `null`/`EMPTY` only for a readable empty slot. A Disk.4 continuation scene is never captured or restored into, Disk.4 provenance is refused, and a pending Earth offer blocks capture. Old version-less saves migrate only when no unit/ship marks are on the map, otherwise `legacy-incomplete`. It is the remake's own record, not Disk.4 export; the exact included/excluded state is in [formats/remake-save.md](formats/remake-save.md). Covered by synthetic tests and scripted `Game.update` menu clicks (`test/save.mjs`; the Game/menu part needs the local Disk.1/Disk.2); the additive accessors it needed are `Sim.rngState` / `restoreRngState`, `Aliens.spawner` / `restoreSpawner`, `MainLoop.restoreAt` / `restoreState` and `EnemySystem.sessionState` / `installSession`.

**Experimental Disk.4 activation (`MapScene.fromPrepared`, `Game.activateDisk4`).** Saved metadata is authoritative: the saved disk id at `$1453E` must match Disk.2 header `+8`, and valid scenario index `$135C2` selects the header table entry (static Disk.1 trace `$888A-$88AA`). Only an invalid saved index can be recovered by caller choice; map matching is advisory. The original `$88AA` scenario-header pointer is written to runtime `$1453A`; the decoded raw area-B copy and input bytes remain unchanged. The `$875C-$87DA` reset is modelled for system flags, pause, queued day and warning lights, and `$88DC-$88E6` clears all 30 effects. The prepared graph is bound once and the initial frame is inert. RNG restoration and the rest of the original post-load/`$802C` exit path remain incomplete. Activation is static-trace/synthetic only, not original restore fidelity or Disk.4 roundtrip compatibility.

**Fresh scenario startup.** A new `GameState` restores initialized image bytes `$1453E`, marker IDs `$14540+10n`, tank damage `$145A3` and ship-damage table `$145A4..$145A9`. The first fresh map entry queues the day and makes the marker-selected alien without an appearance effect; later scenario selections do not repeat the boot-only alien choice. On the browser scenario/tutorial menu route, the immediate first pass consumes that day before the map is first presented, using neutral input so the menu click cannot trigger a map action. Its pass, draw and date work precede the first VBL countdown, which then counts toward the next pass, matching the static `$157BC` → draw/date → VBL-wait order. These changes follow a static trace of `$866E`, `$802C`, `$157AE`, `$11476` and `$564A`, with synthetic/local-data coverage. Original `$2DCC` placement depends on timing inputs; first-frame alignment remains approximate, and no fresh-start runtime comparison has been run.
